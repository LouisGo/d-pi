## 基建只做当前链路需要的部分

- 单应用工程，沿用 Electron / React / TS / electron-vite / pnpm；按实际切片创建 Main、Host、preload、Renderer 及窄共享合同，不先建 monorepo、DI、事件总线或通用 Manager。
- 从首条真实边界建立严格 TS 检查、Biome、版本化 DTO 与 Zod v4 解析；内部规则以判别联合和 ts-pattern 组织。供应商类型留在适配层，不在每个函数重复校验已可信数据。
- SQLite 先承载 Thread、草稿和提交需要的结构，迁移与恢复随第一份数据交付；不先铺远期业务表、完整 ORM 平台或文件快照库。
- 诊断从首条链路贯穿实际进程，沿用[现有预算和错误归属](../../docs/architecture/diagnostics.md)。日志设施失败与业务存储失败分开：前者不能阻塞任务，后者影响持久提交时必须停止推进。
- S1 正式 GUI 前按[设计系统合同](../../docs/architecture/design-system.md)建立最小语义 token、全局 normal/compact 密度入口与 @shadcn/lint + Oxlint 设计检查；用负样本证明规则拦截有效，用真实切换证明传播。UI 只建立当前切片需要的布局、自有组件、Base UI 和 Hugeicons 接入。Tiptap/Monaco/Streamdown 按功能加入，不先建完整组件库或高保真原型。
- 最小包内运行尽早检查资源/ABI；正式 M1/M2 GUI 与性能验收在对应阶段完成。沿用[随包实验](../../docs/validation/packaged-runtime-evidence.md)的经验，不把旧实验版本当成全部新依赖的锁定值。

## 渐进自用与开发闭环（2026-09-27 访谈补充）

用户要求分阶段、选择平滑切入路径并有推进策略；随后进一步明确：初期不开展自用迁入，只打通关键链路，合适时机再评估切入。此前“以自举为主验收、M1 后迁入”的表述已撤回。以下为本轮选定的工程规划路径，不新增产品能力承诺，不构成编码授权，也不自动批准切换日常开发工具。

| 阶段 | d-pi 承接什么、用户得到什么 | 进入与扩大条件 | 外部保障 |
| --- | --- | --- | --- |
| 建立开发闭环 | 用成熟工具开发 S1–S5，每个切片交付真实可运行行为、验证证据及问题记录 | 按证据核对/必要实验 → 无头 → GUI 顺序，不重复成熟能力验证；不为自用提前终端/浏览器等 M3 能力 | 外部工具负责实施、测试和 GUI 检查 |
| 有限真实试用 | 单 Thread 承接边界清楚、可回退的小修改；首次避开正在承载任务的宿主、存储迁移和升级链路 | 提交/阅读、停止/队列暂缓、草稿及中断恢复已在相关场景验证；早期 S2 演示不视为日常自用资格 | 独立工作目录，外部审查 diff、运行检查和操作 GUI；不依赖 App 已有完整开发工具 |
| 承接完整切片 | 在 d-pi 内完成需求输入、修改、反馈与继续，观察它对真实开发的帮助和阻碍 | 小任务有可核对证据，未解决问题不会阻断下一类任务；按需验证多 Thread/子 Agent，不以一例成功宣称普遍可靠 | 工作构建不随源码热更新；候选构建使用隔离的 App 数据和会话，配置副作用单独隔离 |
| 扩大日常使用 | 将已证明合适的任务逐步迁入，再评估是否作为主要开发入口 | 收益超过维护/绕路成本，相关恢复路径可靠；依据使用证据决定，不绑定 M1/M2 标签或日历 | 保留已验证构建及外部修复入口；版本降级不能直接打开已升级的不兼容数据库 |

每个任务开始前明确目标、范围及验收条件；实施后记录构建/代码版本、检查结果、真实 GUI 观察与未覆盖项。发现的问题回到既有任务记录，不另建自动研发平台。影响输入保留、执行控制或结果可信度的故障出现时，暂停扩大自用范围，改由外部工具修复并复测；不自动重发结果未知的任务。

日常自用只是验收证据的一部分，不替代下面的故障、并发、恢复及新用户路径专项验证。用户已确认：每形成一段完整、可操作的用户体验，就交给用户试用；内部实现和自动检查持续推进，影响后续方向的反馈先对齐，无关工作继续。不要求每个内部实现步骤都等待审批，也不等到完整版本才集中体验。依据与纠正见[访谈第二十二轮](../pre-coding-interview/spec.md#第二十二轮自举开发的提出与纠正候选不作为近期前提)。

## 跨模块验收场景

这些是将来验证行为的样本，不是要求现在编写测试框架；实现时选择能发现实际错误的最小测试。公共性能数值集中在[基础契约 §7](../../docs/architecture/foundation-contracts.md#7-诊断与性能验收预算b6)，本次不新增未测预算。

| 场景 | 必须观察到的结果 | 主负责 / 协作 | 阶段与证据方式 |
| --- | --- | --- | --- |
| A1 正常提交、回答、继续 | 原生真实执行；收据、显示与草稿版本一致 | 执行 / 输入、宿主、阅读 | M1：真实 OMP + GUI |
| A2 派发前存储失败 | 未写 OMP，草稿/内容可恢复，具体阶段可查 | 存储 / 执行、输入 | M1：故障样本 + GUI 反馈 |
| A3 写出后未确认 ACK 就断链或 ACK 收据写失败 | unknown，不自动重发；重启仍保留原内容 | 执行 / 宿主、存储 | M1：可控断链/崩溃 + 重启 |
| A4 提交中继续编辑，迟到成功或错误 | 原提交得到正确结果，新草稿不被清空或覆盖 | 输入 / 执行、存储 | M1：时序样本 + 真实输入 |
| A5 停止时有队列/干预/待答 | 区分请求中断、当前执行结果和残留活动；停止后保留且暂缓队列，明确继续才恢复，验证下一条消费竞争与失败；观察干预/停止的实际作用范围 | 执行 / 宿主、阅读 | M1：原生组合场景 + GUI |
| A6 窗口关开、Host/OMP 分别故障 | 关窗继续；故障范围正确；旧连接不污染；恢复不重放输入 | 宿主 / Thread、执行、阅读 | M1：真实进程与窗口 |
| A7 重连恰遇增量、分页 busy/缺口 | 快照水位衔接；可恢复记录的最终内容、来源与关联和实时结果一致，缺口明确 | 阅读 / 宿主、存储 | M1：确定事件样本 + 忙碌原生读取 |

## 结论

本轮重拉主线、重新构建，并在真实 Electron 窗口点击复测。上轮 A、B、D、E、F 的针对性改进均已看到；C「完整退出后继续旧会话」仍未实现，当前明确保留冷恢复只读。

不能据此给出整体稳定性通过：本轮两次复现未退出应用时，两条原生会话同时中断。它与 C 的冷启动策略是两件事，根因未定，详见下文。

整个测试不依赖模型：没有真实凭据、没有模型生成，没有向供应商发送认证请求。真实生成、流式输出、工具、停止与后台任务仍未验证。

## 新观察的未退出会话中断

### 首次观察

先后启动 alpha 的两个无模型 Thread，读取 beta 的合成历史，再在 alpha/beta 间切换与后退/前进。没有发送消息，也没有关闭窗口或退出应用。02:07:42 UTC 两条原生连接在 8 毫秒内先后记录 `disconnected / exit`，随后 UI 变为「原生连接已中断、只读」；三行草稿仍在（截图 15）。

同一时段，四个配置快照子进程的请求出现约 25.8–26.1 秒超时，历史发现/读取失败。安全诊断可确认事件顺序，但没有子进程退出码或信号，所以无法区分 SDK 崩溃、外部终止、资源压力或 watchdog 自终止。

### 窄范围复现

真正 Quit 后重开同版，重新建两个已启动、无模型 alpha Thread，进入 beta 历史后依次选 alpha、后退、前进。第二轮没有并行 build、认证 fixture 或其他测试。02:13:33–34 出现四个配置快照子进程；02:15:45 两条新原生连接再次在 8 毫秒内退出，四个快照以约 131 秒超时结束，历史读取失败。真实 UI 再次变为只读（截图 20）。这次短序列在本机重现了中断，不能按偶发未复现处理；没有证据将时间数字外推为稳定性能基准。

### 归因边界

- 这是需要跟进的暖会话中断，不能归进「Quit 后只读是设计如此」而忽略
- 普通 Thread 导航不应主动关闭原生会话；代码的受控关闭路径也与这次 `disconnected` 顺序不同
- 本机此前 build 被系统以 137 结束，限制 Node 堆后成功；这只支持存在环境资源约束的可能，不能证明会话中断就是 OOM
- 旧版已有 watchdog 每 500ms 同步检查父进程身份，`ps` 超时 1.5 秒即可能被视为身份不匹配，并终止进程组；这是具体可调查机制，不是已证实根因
- 生命周期/watchdog 代码相对上轮 fe03c4f 未变，因此也不能把异常直接归罪于本次五项 UI 修复

建议把这项列为高优先级稳定性问题：先记录 native exit code/signal 与 watchdog 判定原因，检查快速导航下配置/历史查询的并发与取消，再在有余量的环境复现。不要通过解除只读保护掩盖连接中断。

源码：[退出信息处理](https://github.com/LouisGo/d-pi/blob/7ae6962c5f6e6903964f429d5d5f904b99d18c08/src/modules/execution/host/native/native-session.ts#L84-L105)、[watchdog 身份检查](https://github.com/LouisGo/d-pi/blob/7ae6962c5f6e6903964f429d5d5f904b99d18c08/src/modules/execution/host/native/native-bootstrap.ts#L8-L20)。

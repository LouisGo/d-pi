## 新会话起点 提交与并行协作

新会话从包含本规格与复盘记录的准备提交创建 `codex/` 工作分支，核对实际 HEAD 和工作树；`59256015` 用于查设计依据，`4adea82` 用于现状与冷启动对照，不自动 reset 到历史提交。不同 checkout 需要先带入准备提交；不复制个人生成资源或配置。重写完成有问题的实现可以替换其内部结构，不要求维持每一个旧类或补丁形态。

开始先读根 AGENTS、本规格的推进与交接及有关现行决定；模块、合同和 skill 随任务读取。复盘记录是按课题查询的历史索引，不要求重新审计全部 32 条提交。已有事实足够就进入对应工作，不把所有准备检查变成全仓串行前置。

通常采用 **主 Agent + 2 个实现子 Agent**。主 Agent 负责范围、共享合同、任务依赖、集成、验证调度、工作记录与本地提交。根据阶段安排角色：

| 阶段 | 子 Agent A | 子 Agent B | 主 Agent 的重点 |
| --- | --- | --- | --- |
| 文档与工程入口 | 文档职责、导航和 skill 校准 | 环境复现、机器门禁和测试入口 | 冷启动对照、现行决定、跨文件约束与集成 |
| 核心实现 | 初始化、存储与提交事实链 | 展示状态、只读查询与编辑器接入 | 跨进程合同、OMP/诊断边界与完整用户路径 |

角色不替代具体文件边界。每次委派明确目标、可写文件、共享接口、真正依赖、验收和返回证据；一个文件只设一个写入者，共享 schema、package/lockfile 和根配置由主 Agent 协调。子 Agent 不在共享工作树切换分支、回退或抢先提交；必要隔离使用独立工作树，安装、资源生成、构建和打包也要隔离或串行调度。

初始化、提交/恢复、跨进程合同等重要波次，在 diff 或提交冻结后可启用第 3 个子 Agent 独立审阅。当前通常最多主 Agent 加 3 个子 Agent 同时工作，并遵守实际工具上限；只有独立任务有收益时增加角色，不为凑数创建 Agent。主 Agent 核实发现并整合必要修复，不把子 Agent 的自报通过当作最终验证。

冷启动评测子 Agent 与实现子 Agent 分开：使用新上下文（支持时 `fork_turns: none`），只接收同一任务、工作目录和普通项目入口，不注入本轮复盘答案、评分清单或主 Agent 的调查上下文。评分标准由主 Agent 持有，仓库自身随版本变化的规范仍可按普通入口读取。

本地 commit 的必要节点：准备与计划基线、完成的文档迁移波、可复现工程入口、每个完整核心行为切片、必要补修与最终交接。不按文件数量提交半成品。提交前检查 diff、相关验证和阶段记录，主 Agent 只 stage 当前范围；文档搬迁、纯机械调整与业务修改分批。收尾报告 commit SHA、实际验证、未覆盖项和试用状态，不 push。

准备提交只包含规格与复盘；干净环境、冷启动与行为回归由执行会话补齐，其实际完成和限制见上方推进与交接，不从准备态推断当前状态。按仓库任务约定拆最近的实施票，不一次细化整个远期计划，不新增平行状态文件。

## 三 校准 Skill 与状态查询范式

每条规则清楚归入项目政策、库的事实或推荐范式。政策说明选择理由与边界；库事实注明核对版本和成立条件；范式指向经过验证的源码入口和典型反例。当前代码有已知问题时不能把它当作推荐范式，先修正并验证，再更新引用。

优先引用真实实现，短示例只解释源码不易表达的关键点。内容明显变长时再拆 `references/`，不机械拆短 skill，也不把同一规则复制到合同、skill、模块页和 AGENTS 四处。

保留并准确表达三条政策：

- **事实所有权**：同一可变事实不能由 Query 与 Zustand 独立双写。允许同一 Thread 的历史分页与实时尾部各自保留范围明确的投影；重叠时按领域身份与版本规则合并、去重，不成为两份可独立修改的正文权威。相关功能实施时才接入，不提前扩展历史分页。
- **执行命令**：发送、回答、停止、继续等沿用协调器与收据合同，不由查询缓存、重试或恢复机制自动补发。该规则来自 D-24 的业务选择，不能解释成 Mutation 在所有配置下必然重试或重发。
- **生命周期**：业务实例由应用或 Thread 作用域拥有；视图卸载释放订阅和编辑器资源，不等于停止业务任务。跨异步边界继续验证身份、代次和版本，dispose 保持幂等。

Zustand/Query 的推荐写法围绕实际责任建立：

| 责任 | 范式与验收 |
| --- | --- |
| 展示状态 | Zustand vanilla store 与 React 绑定分离；选择器返回稳定值或引用；整体替换与浅合并按状态语义选择 |
| 生命周期协调 | 保留真实必要的身份与代次守卫；内部资源状态与展示投影分清，避免无意义通知；不以每个模型必须包三套订阅 API 为目标 |
| 实体列表 | 保留未变化实体引用；在更新频繁的列表评估 ID 顺序和实体索引，不能只证明少渲染而忽略所有行的重复查找成本 |
| 查询身份 | key 表达影响结果的稳定资源身份，区分未选中与合法默认值；bridge 对象本身不能代替资源身份 |
| 查询定义 | hook 与命令式读取共用领域的 `queryOptions`；各消费 API 的执行条件仍按自身语义核对 |
| 本地读取 | 显式 `networkMode: 'always'`；缺失、拒绝、二进制、超限、变化中和非 Git 等业务结论按数据返回；采样失败进入错误通道才可能重试 |
| 刷新与缓存 | 缓存不冒充当前磁盘事实；区分旧数据、重新采样和失败。沿用已确认交互，新增保留/清空策略须按实际产品影响处理 |

优先校正现有 [state/query skill](../../.agents/skills/d-pi-state-query/SKILL.md) 的三处过度概括：完整 `StateCreator` 标注不是唯一合法写法；禁用查询有缓存时不必是 pending；项目禁止执行命令走 Mutation 的理由应写成业务政策。初始化推断和选择器重载用项目锁定版本验证，不制造新的全仓库禁令。

查询定义与 key 的库事实对照 [Query Options](https://tanstack.com/query/latest/docs/framework/react/guides/query-options) 和 [Query Keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)；官方当前文档用于核对概念，项目锁定版本源码与行为测试决定实际适用性。

**验收**：规则有条件，范式有真实入口，代表性行为成立；skill 帮助 Agent 选择正确实现，不把历史补丁变成永久约束。

| [原生事件名称包装](../../src/platform/omp/protocol/native-frame.ts) | 在消费边界解析已知 payload 的必要字段；未知事件保持开放 | 已知事件得到可用类型，未知事件不伪装成已知能力 |
| [读取日志时序](../../src/app/main/ipc/project-reads.ts) | 起始阶段在 I/O 前记录，终态在实际完成或失败后记录 | 请求挂起时已有 received；终态、原因和耗时覆盖真实操作 |

接口与抽象以能否减少非法状态、重复责任和信息损失判断。函数与参数足够时直接使用；共同的名字或相似的几行代码不自动要求建立包装层。注释解释不变量和难以察觉的原因，迁移过程放在工作记录。

| 内容 | 做法 |

## 五 收口开发基建与干净环境

### 1 启动和资源

当前 README 要求 `runtime:fetch`，而 [S3 正式路线](../m1-s3-control-recovery/handoff.md) 要求 `runtime:sdk`。迁移 README 时按当前生产代码核对并收口：

- `runtime:sdk` 从锁文件和已安装依赖准备官方 SDK、Bun、App 薄宿主、消费门控与资源 manifest，是当前 SDK 路线所需准备步骤。
- `runtime:fetch` 下载并校验固定的官方 CLI artifact，用于仍保留的对应验证路径；不能作为 SDK 资源已准备的证明。当前 artifact manifest 为 `darwin-arm64`，不宣称其他平台已支持。
- 安装、SDK 资源准备、`pnpm check`、`pnpm build`、`pnpm dev` 和 `pnpm package:mac` 各自说明产物、前置条件与支持范围。优先复用现有命令，只在确有重复步骤时增加薄的聚合入口。

干净环境检查使用独立 checkout/目录及独立资源输出，不依赖作者机器的 `resources/sdk`、全局 OMP 或未记录的缓存。明确依赖包仓库可访问和离线缓存需求，不把可复现承诺成无网络安装。

### 2 工具链与环境检查

开发环境以 **Node 24.21.0 / pnpm 10.5.2** 为本轮固定目标：前者有 [完整检查通过记录](../state-query-alignment/issues/04-integration-verification.md)，后者是当前 `packageManager`。落地单一版本入口，并用干净环境的检查、构建和 SDK 冒烟确认；失败时根据证据修正组合，不静默跳过检查。现有 `engines >=22.19.0` 是最低声明，不是精确的开发环境或全部版本验证结论。

开发 Node、Electron 内嵌 Node 和 OMP 宿主 Bun 分别记录。当前依赖固定 Electron 44.4.5、Bun 1.3.14、OMP 18.3.0；Electron 内嵌 Node 从实际进程报告，不能由开发 Node 或类型包版本推算。

环境检查报告这些版本、平台/架构、SDK manifest 与资源缺口，并指出 `ELECTRON_RUN_AS_NODE` 等会改变启动语义的异常变量。工具未启动与规则失败分开，修复建议明确，不能自动绕过错误造成假通过。

### 3 隔离和检查分层

自动测试同时隔离 App 数据、OMP 配置与会话目录、测试工作目录和项目配置/扩展。启动子进程使用受控环境，不继承个人 API key 或凭据；确需扩展或 provider 时用明确 fixture、本地服务与测试凭据。只设置 `D_PI_DATA_DIR` 不足以隔离 OMP。

本地 hook 只运行快速稳定的检查，并检查该检查消费的必要配置/依赖；CI 复用现有完整检查与构建。原生进程、SDK、资源准备或打包路径变化时，补受支持平台的相关集成验证。初次建立完整基线，后续按受影响路径检查，不把每次文档修改扩大成原生矩阵。

**验收**：新环境依 README 完成准备、检查、构建与受支持启动；生成资源可重建，测试不接触个人配置，异常环境有明确诊断。

## 六 核对 OMP 接入与诊断证据

先检查现有 Runtime 合同、Host 适配和投影。在具体能力边界修正类型泄漏、字段解释或版本耦合，沿用未修改的官方 SDK 薄宿主路线。当前工作不自动升级 SDK。

| 验证 | 能证明什么 | 使用条件 |
| --- | --- | --- |
| 脱敏真实事件样本回放 | 已知输入的解析、关联与投影 | 相关边界改动；保留关联字段、顺序及样本版本，真实与合成样本分开标记 |
| 固定或候选 SDK 的真实行为测试 | 所测版本仍满足关键执行语义 | 关键适配改动使用固定版本；考虑升级时才测候选版本 |
| 打包后的集成冒烟 | 随包资源、进程和通道在交付环境成立 | 原生/资源/打包改动及相应交付节点；用迁移后的包与隔离配置 |

优先复用已有证据与 fixture。资料无法回答的关键未知才补最小实验；缺少真实样本就如实记录，不用合成回放冒充真实接入。关键样本优先覆盖 ACK 后异步失败、停止与下一条消费竞争、继续原队列、unknown 不重发、窗口重连与进程中断。断言业务语义，不机械比较完整 JSONL；旧记录回放不证明候选 SDK 的行为兼容。

诊断从用户错误的 traceId 出发，能够沿实际经过的应用边界找到最后确认位置与证据缺口。请求进入、派发、接受、执行结果和失败不能合并成一个 success；错误保留来源、原因与处理归属，未证实根因保持 unknown。日志继续轻量、异步、有界。

先提供可执行的故障阅读步骤；诊断包导出在这条路径成立后按功能范围接入，不新建观测平台或默认外传机制。导出说明版本、覆盖与缺口，避免把原生业务全文直接复制为诊断包。

执行不可用与内容可读分别表达。存储格式、配置与历史读取路径兼容时，草稿、冻结发送记录和原生历史保留访问路径；不承诺读取损坏或不兼容的数据格式，不靠删除数据库、伪造 ready、自动重发或新建替代会话恢复工作。持续单写证据不足继续只读。

**验收**：能说明发生了什么、最后确认到哪里、还不知道什么，以及用户目前可做的安全动作；验证结论标明对应版本和真实覆盖。

## 七 用同组 Agent 冷启动任务作对照

基线使用上文记录的现状提交，复测使用每批或最终明确的提交。两侧采用同一任务描述、期望行为和隔离环境，固定模型、推理配置、工具权限、预算、外部全局指令与可访问的记忆范围。每个任务开启新上下文，不继承本轮复盘或另一轮结果。

仓库内 AGENTS、skill、文档与实现是被测改动，按版本加载，不强行保持内容相同。记录外部文档访问条件及环境差异，无法控制的因素注明；一次成功不足以声称普遍效率提升，失败、波动或关键疑点时再做必要复测。

| 任务 | 通过标准 |
| --- | --- |
| 新增本地文件查询 | 复用正确入口；资源身份、缓存、离线读取、业务 unavailable 和采样错误处理成立 |
| 修改组件密度 | 沿用全局 token/组件合同；读取与任务有关的材料，无需重建执行与恢复历史 |
| 调整跨模块接口 | 找到事实拥有者、公开入口和环境边界；实现与依赖清单一致 |
| 设计未知提交恢复入口 | 提出保留内容、显式重复风险与只读限制的方案；不触发真实重发或伪造接受结果 |
| 判断可继续的工作 | 区分现行授权、历史限制、工程完成、待试用和用户认可；给出有依据的下一步 |

任务涉及实现时使用独立工作区，任务涉及设计时交付方案即可。先评价正确性和关键约束，再记录误读、重复确认、无关阅读、token/时间等实际可得成本。不以读得最少、固定文件阅读顺序或一次最好成绩作为通过标准。

**验收**：正确性不退化、关键约束可发现并落实，接手成本的改善有可复查记录；不为评测搭建新平台。

## 八 执行顺序与完成标准

| 波次 | 交付 | 放行依据 |
| --- | --- | --- |
| 0 | 记录基线、合同与同组冷启动任务 | 对照点、隔离条件和判定标准明确；不提前回退覆盖现状证据 |
| 1 | 文档入口、状态职责与 skill 校准 | 引用正确，现行依据不丢失，状态不复制，错误规则已纠正 |
| 2 | 机器检查、工具版本与干净启动入口 | 负例确实失败，测试进入标准入口，新环境准备/检查/构建/启动成立 |
| 3 | 按功能重写核心问题实现，补受影响 OMP/诊断证据 | TDD 验证目标缺口；正常路径、事务、恢复和身份边界成立；必要 GUI 与试用交接明确 |
| 4 | 同任务复测与结果交接 | 对比正确性及成本，记录未覆盖项、真实构建和后续边界 |

该顺序表达主要依赖，独立工作可并行；不要求全仓文档完美后才进入有足够依据的实现。沿用项目 TDD 与验证投入合同，不新增一套测试流程。每批独立提交，记录实际改动、验证与未覆盖项；文档搬迁、纯机械目录调整与业务修复分批。具体提交、推送、回退和实施动作遵守当时的明确授权。

公开试用分发前另完成版本与发布基础：采用递增的预发布序列，如 `0.1.0-alpha.N`；切片和 Git SHA 独立记录，序号依据真实发布记录确定，不能把例子中的数字当起号。build metadata 不参与版本优先级，遵循 [SemVer](https://semver.org/#spec-item-10)。现有 `0.1.0-s4.0` 高于同基础版本的 `0.1.0-alpha.N`，不能直接改名并声称递增；按真实分发记录确定基础版本并核对升级路径。项目自身许可证待权利人确认，贡献入口、安全报障方式和第三方随包声明按实际分发范围补齐；这些准备不构成公开发布授权。

**完成标准**：规则少重复，现行依据容易找到；核心实现减少非法状态与重复责任，关键错误更早暴露；开发与验证可复现；同组任务有正确性与成本证据。目录、ADR、检查器数量以及单纯删行数不作为完成标准。工程完成与用户体验认可继续分别记录。

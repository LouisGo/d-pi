# 目标与边界

先明确产品需求，再做技术选型。以下能力清单记录最终需求，不代表首阶段全部实现；首阶段方向已确定为主对话流程、只读代码查看与 Diff，编辑能力后续渐进加入。现有 OMP 职责与配置决策继续保留，若新增需求触及其边界，再明确讨论。

## 2026-09-25 已确认的增量决定

- 模型选择不设 GUI 自有白名单；首版新增认证入口按 D-23 限于 OpenAI 账户登录和 DeepSeek API key，已有其他可用配置仍复用；承接随包兼容 OMP 在当前配置下提供的供应商、模型和原生自定义配置能力。模型可用性、凭据和模态限制按 Runtime 实际状态表达，不把尚未验收的 GUI 认证流程假装成已实现。
- 已有可用 OMP 配置的用户直接进入应用并复用配置，无须重复初始化；没有原生配置的新用户使用 GUI 分步引导，参照 OMP TUI 的实际流程改善呈现。判定依据是原生配置/认证是否可用，不只是 PATH 中有没有 omp；不复制另一套凭据和配置规则。配置缺失、失效或版本不兼容时只引导补齐受影响部分，不覆盖已有配置。
- 应用仍使用随包 OMP，不因本机安装了 CLI 就切换到外部可执行文件；初始化具体步骤需在实施前核对固定 OMP 版本，不把建议步骤冒充既有 TUI 步骤。
- 编辑器已选定 Monaco；首版只读与 Diff，后续达到既定 B 档。Code-OSS / OpenVSCode / monaco-vscode-api 不再作为当前并列路线，保留研究历史。
- Composer 曾研究直接 ProseMirror 与最小 Tiptap；2026-09-26 已由 D-33 确认最小 Tiptap，取代此处原待定状态。比较理由保留在[研究](composer-research.md)，不把已选路线写成性能已验收。
- Git Panel 围绕 OMP 工作流自建 GUI，Git 数据和操作复用成熟实现；“20% / 80%”表示职责取舍，不是工作量保证。不建设完整通用 Git 客户端，也不以寻找大型可嵌入 Git GUI 作为前提。原 B 档操作作为按场景渐进覆盖的能力清单保留，不以此扩张通用客户端范围。
- 从设计起点为 Agent Changes / Run Changes / Review / Revert 保留结构与能力接入位置，不要求首版显示不可用按钮。名称还不是完整领域契约：Run 范围、改动归属、Review 状态、Revert 的对象/基线/并发处理需在相应阶段确认。Revert 不自动等于 git revert、丢弃工作区修改或 OMP 会话回退；此前原生会话回退决定仍有效。
- 未回答的后续阶段问题保持待决，本轮不追加默认选择。

## 应用日志与监控（2026-09-25 用户确认，D-21）

从开发开始为 Electron 应用每一层建立结构化、可追溯日志与基础监控，放在架构横切基础层；日常无感，必要时可读取、筛选和导出定位问题。OMP Runtime 内部不改。用户补充：不追求 DeepSeek Harness 式极致体系，不让日志影响正常体验；专用日志界面可以以后做，不是首版前置。以异步、有界、按需详细记录和性能验收落实，不能把“无感”宣称为未经验证的零开销。见[诊断设计](../../docs/architecture/diagnostics.md)。

D-22：同一次操作在 Renderer、Main、utility 等实际经过的应用层使用统一 trace ID，可检索阶段、耗时与错误链。明确异常类型、处理责任与归因证据，区分应用自身错误、OMP 报告错误和未知根因；OMP 不保证无 bug，但归因不能靠猜。此要求不把专用日志界面提前。

## 首阶段交付方向

2026-09-25：用户要求先完成首版验收、Composer、变化记录三项收敛并持久记录，再开始动手。[具体方案](foundation-plan.md)已随后按七项答复收敛阶段与基础合同，组件候选仍须验证；[决定登记](../../docs/decisions.md)区分已确认和提议。

- 用户接受先只读、后编辑的渐进方式。首阶段围绕“打开项目 → 提交需求 → 观察执行并回答交互 → 查看结果与代码差异 → 继续或恢复会话”形成可用流程。
- 文件查看与 Diff 作为首阶段能力；不要求第一版完成 B 档代码编辑与语言服务。终端、浏览器、完整 Git 操作及其他最终能力可后续逐项接入，不据此移出最终目标。
- 具体批次已由 D-26 和[基础契约 §8](../../docs/architecture/foundation-contracts.md#8-开发入口里程碑与门槛b7)明确：M1 内部闭环包含文字/选区及基本交互，M2 首版包含全部指定输入与 V1-00–10 验收集合；其余原生能力按 M3 渐进覆盖。不能把 M1 可运行当作 M2 或 TUI 全集已完成。
- 六组技术选型的初步评估见 [技术选型评估](technical-evaluation.md)，建议与待验证项分开记录，未安装依赖或建设产品应用。

## OMP TUI 全量承接与组件建设

- 最终覆盖目标是基本完整承接 OMP TUI 可展示的内容与相应交互，在 GUI 中提供更精细的呈现，不预先按“简洁模式”删减信息或能力。
- 全集是最终覆盖目标，开发与交付采用渐进方式：逐项增加能力，每个阶段都可交付可用成果，不要求全部功能或展示入口建成后才交付。
- 能力清单用于追踪最终覆盖方向，可随调查与开发持续补齐，不是启动开发或交付的全集盘点门槛。分批实现时，不把尚未实现的能力当作已决定删除。
- 每阶段都可开展产品测试，调整已实现能力的默认折叠、摘要与展示层级；无需等待全集完成后才做体验取舍。简洁展示不能成为未经讨论就永久删减最终覆盖目标的依据。
- 前期基础建设围绕可复用的技术组件与业务组件展开。技术组件候选包括编辑器、Diff、终端、Markdown、附件与图片展示等；业务组件候选包括消息、工具调用、执行状态、子 Agent、待回答交互与历史导航等。此分类为设计起点，具体边界依据 OMP 的真实数据与交互确定。
- 优先复用成熟开源技术组件；业务组件承接 OMP 原生语义，避免各页面重复解析事件或自行定义另一套执行状态。组件应能承载完整详情，并支持后续按产品测试结果调整呈现层级。
- 完整覆盖需逐项区分：TUI 可见内容、原生交互、Runtime/SDK/RPC 可接入程度、GUI 组件与验收场景。TUI 已有能力不自动等于 GUI 接口已经齐备。
- 覆盖矩阵与组件需求依据固定 OMP 版本逐步建立，为当前阶段的选型和实施提供足够依据即可推进；不要求先穷尽所有功能或建完全部基础组件。此处尚未完成全集盘点；已有自有组件层与候选库记录继续有效，见[库雷达](../../docs/prototype/frontend-library-radar.md)，不因清理实现而重置。

## 平台范围与决策规则

- 优先 macOS 开发与验收；Windows、Linux 的交付时间和支持程度尚未承诺。
- 后续需求讨论、技术选型和开发中，任何拟采用的 macOS 独占功能或必需能力，必须先向用户汇报，由用户决定是否接受，不能自行作出平台范围取舍。
- 汇报需说明独占原因、受影响的平台与功能，以及可行替代方案；决策前暂停依赖该选择的部分，其他独立工作可继续。
- Electron 作为跨平台基础，不等于所有依赖和功能自动跨平台；原生模块、系统 API、外部工具与平台行为仍需核实。未在其他平台验证的能力不得标记为已兼容。

## 已确认需求与待决边界

| 能力 | 最终需求 | 待明确 |
| --- | --- | --- |
| 历史编辑、分叉与回退 | 直接对齐 OMP 的产品定义与原生会话行为，通过 UI 方便地选择历史消息、编辑后重新执行、分叉与回退 | 核实桌面接入能力与原生行为的一致性；不另行定义文件恢复选项或自研回退语义，不能把会话回退标为文件回滚 |
| 多 Thread 与工作目录 | 同一项目支持多个 Thread 并行工作；既可直接使用项目目录，也可使用独立 Git worktree | 创建、恢复、清理与目录关联的桌面接入流程；共享目录不意味着文件修改隔离 |
| 内置浏览器 | 支持本地项目预览、外部网页浏览和登录；使用一个持久化浏览环境，在应用内共享登录状态，不做按项目隔离或多账号环境；AI 操作浏览器为后续目标，预计接入 computer use | 具体嵌入与 computer use 方案待选型；AI 使用当前页还是独立标签页未确认，可在该能力实施时讨论 |

| 终端 | 提供类似 VSCode 底部面板的集成终端，可通过 Command + ` 快捷键唤起，供用户直接输入命令并运行程序 | 多终端及进程生命周期细节后续设计；用户未要求接管 AI 执行的命令，具体实现留待选型 |
| Diff View | 必须提供可跨场景复用的代码差异展示组件，可用于单轮变化、会话累计变化、Git 未提交变化等场景，不绑定某一种业务定义 | 具体展示与交互能力待设计；各使用场景分别定义数据来源与对比基线，不由组件统一决定 |
| Git 可视化管理 | 先覆盖 B 档：状态、分支、历史、提交详情与差异查看，以及暂存、取消暂存、提交、拉取、推送、创建与切换分支、冲突解决；保留 C 档进阶操作的扩展可能 | 采用自有 OMP Git Panel + 成熟 Git 实现；不做完整通用 Git 客户端，具体操作按阶段接入，C 档不预先扩张 |
| 子 Agent 默认设置 | GUI 按 Agent 定义设置默认模型/思考档位，由主 Agent 正常调度，后续 spawn 生效 | 恢复既有 D-27；原生配置通路已验证，GUI 后续交付；不做运行实例热切换 |
| Side Chat | AI 作答期间或完成后针对文本或段落发起独立问答，可继续追问；携带选中内容及发起时的主会话上下文，只读查看项目代码；模型与思考档位可独立切换；历史保留并关联主 Thread 和原文位置，可显式同步主会话最新进展 | 上下文容量处理、可用模型及其支持档位、切换对正在生成回答的生效时点 |

| 段落图片分享 | 选择回答中的一段或多段，生成排版美观的分享图片，保留代码高亮、列表等格式；提供统一默认样式，支持复制图片、保存 PNG，长内容可拆成多张图片 | 具体视觉样式与分页细节留待设计；此需求为内容排版导出，不包含 AI 绘图或在线分享服务 |
| 视图分屏 | 当前不做分屏，采用常规布局 | 早期上下、左右分屏设想暂缓，不作为当前交付或选型的硬性要求；是否恢复后续再议 |

## 首批语言支持与宿主语言评估

- 工程质量工具已确认采用 Biome 取代 ESLint + Prettier；仅在搭配 @shadcn/lint 时引入 Oxlint。该选择约束应用自有代码，不修改用户打开项目的格式化约定。
- 用户要求重新审视 Markdown、VSCode 复用与复杂 composer 选型：技术评估已改为 Streamdown/Shiki 单一渲染入口、Monaco 已选定，以及现按 D-33 采用最小 Tiptap 的真实输入场景验证。上述方向不代表已完成集成验收。

- 已确认首批重点是 TypeScript、JavaScript 与 Node.js 项目；Node.js 在这里是目标运行环境，不是另一种编程语言。编辑器应围绕这类真实项目验证补全、跳转、引用、诊断与格式化。
- 助手评估建议（尚非用户确认的最终选型）：应用自有桌面逻辑采用 TypeScript，宿主服务运行在 Electron 提供的 Node.js 环境中；当前没有足够理由再引入 Rust、Go、Python 等自研后端语言或独立 HTTP 服务。
- 依据：现有 Main / utility SessionHost / 独立 OMP 边界已明确；[随包实验](../../docs/validation/packaged-runtime-evidence.md)验证了 Renderer → Host → OMP 往返与退出。该实验只证明基础链路，不代表完整产品性能或所有原生组件兼容性已验证。
- 自有宿主服务主要负责 Runtime 生命周期、协议适配、文件与进程操作及 App 偏好；Agent 执行和原生会话继续由 OMP 拥有。Git、终端、语言服务优先集成成熟实现，依赖内部使用原生语言不意味着项目需要自研第二套后端。
- [Electron utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process)提供带 Node.js 与消息端口的独立进程；[Node worker_threads](https://nodejs.org/api/worker_threads.html)可用于 CPU 密集 JavaScript 工作。进程与线程按实际负载分配，不把所有工作堆到 Main，也不为每项能力提前创建独立服务。
- 重新评估语言的触发条件：实测性能瓶颈无法通过现有实现或任务隔离合理解决；必要系统能力缺少可维护的接入；已有成熟组件要求额外运行时。优先局部集成，不据此整体改写宿主层。macOS 独占能力仍须向用户汇报。

## 历史决定与验证的延续

此前已确定并验证过关窗继续、重新打开接回、真正退出时等待/停止/取消，以及部分刷新恢复和故障场景，详见[当前交接](../../docs/prototype/handoff.md)。这些不再作为全新问题反复询问。旧单会话范围和未验收项保留为阶段历史；新需求取代关系见[架构整理](../../docs/prototype/v1-architecture-draft.md)。组件层采用自有 API 与设计变量，shadcn/ui、Beautiful UI、Tool UI 按既有定位参考和复用，不自动换成外部整套组件契约。

## 输入体验

- 用户明确上述输入方式全部需要，并强调对输入体验要求很高；不能仅以“能够提交”为体验验收标准。
- 已确认：文字输入、截图粘贴、图片/文件拖入、PDF 等文档附件、@ 项目文件引用、编辑器选区附加到主对话或 Side Chat。
- 代码选区附加时冻结原文、路径和行号；@ 文件发送准备时冻结，附件导入时复制保存。来源变化和转换缺口明确展示，见[基础契约](../../docs/architecture/foundation-contracts.md)。
- 具体模型能否读取附件需核实并在界面明确提示；接受附件不等于模型实际取得内容，也不承诺所有模型原生支持所有文件格式。
- 草稿保留、附件预览/移除、准备/失败状态、冻结提交及 unknown 不自动重发按本轮采纳的基础契约执行。

## 主会话执行期间的输入

- 普通发送默认排队追加：当前工作继续，后续再处理新要求。
- 提供独立的干预入口，用于要求 AI 尽快调整当前工作；提交成功不等于已经采纳，也不承诺立即打断正在执行的工具。
- 提供独立的停止入口，用户可明确停止当前执行，再决定下一步。v18.3.0 旧实验已确认 abort 不清 follow-up 队列，存在 steer 时队列可能继续，见[历史实测](../../docs/archive/stage1-evidence.md)；接入时区分“已请求中断”、当前执行实际结果和剩余排队/后台活动，不能收到 abort 回执就显示整项任务“已停止”。M1 前按[基础契约 §1](../../docs/architecture/foundation-contracts.md#1-身份持久化与生命周期b1)验证组合场景；不将停止理解为清空队列或撤销修改，新增全面停止语义须另行对齐。
- Side Chat 保持旁路问答，只有用户显式发送结论到主会话时，才进入主会话输入流程。

## Side Chat 的已确认行为

- 不打断主会话执行，不修改文件，不自动向主会话追加指令。
- 自动携带选中段落与提问时的主会话上下文，可以只读查看项目代码并继续追问。主会话继续运行期间，项目文件可能变化；此需求不意味着文件内容也已具备快照隔离。
- 用户可显式将讨论结论“发送到主会话”；进入主会话后的排队追加或干预行为仍须遵循对应交互约定。
- 用户可独立切换 Side Chat 的模型和思考档位，不改变主会话设置。具体模型支持哪些档位留待 Runtime 能力核实，不承诺所有组合均可用。
- 关闭面板不删除对话，可重新打开并继续；每段 Side Chat 关联发起它的主 Thread 与原文位置。
- 初始使用发起时的主会话上下文，后续追问沿用自身对话，不自动同步主会话的新进展；用户可显式同步最新进展。

## Diff View 与 Git 的边界

- 2026-09-25 用户确认 D-20：首版交付 Git 当前差异与有原生证据的工具修改，并明确标注来源；完整 Run Changes 和逐次修改归属后续接入，先保证来源准确。不把全部工作区变化冒称为 AI 改动。

- Diff View 是通用展示组件，不是“这次 AI 改动”的业务概念，也不要求用户在单轮、会话累计、Git 工作区三类场景之间择一。
- 具体场景负责定义比较对象、时间范围和基线；通用差异展示不自动提供历史快照、改动归属追踪或 Git 操作能力。
- Git Panel 是围绕 OMP 工作流的产品能力，可复用 Diff View，不建设完整通用 Git 客户端。已确认先覆盖 B 档日常操作，并保留交互式 rebase、cherry-pick、复杂分支图操作等 C 档能力的扩展可能，C 档不是当前必交范围。
- GUI 由项目按 OMP 语义组织，Git 机制复用成熟实现；不以引入完整 Git GUI 大库为目标，也不为尚未确定的 C 档需求提前建设自研框架。Agent/Run 改动归属必须有来源证据，不能直接等同 Git 工作区全部变化。

## OMP 工作目录能力核实（2026-09-24）

核实范围为项目已验证的 OMP v18.3.0，不是对最新版本的声明。本轮只读核对源码与上游文档，未运行 worktree 创建或迁移实验。

- 现有[可行性记录](../../docs/validation/runtime-feasibility.md)已实测两个独立 OMP 进程并行会话、历史不串；这不提供共享目录的文件写入隔离。
- [`/wt` / `/worktree` 实现](https://github.com/can1357/oh-my-pi/blob/v18.3.0/packages/coding-agent/src/slash-commands/builtin-lifecycle.ts)同时有非 TUI `handle` 和 TUI 入口，创建 worktree 后迁移当前会话；生成回答期间拒绝该操作。

- 结论：已有可复用的会话/worktree 基础能力，不应重造；桌面创建入口、Thread 与工作目录关联、恢复和清理仍需适配与验证，尚未宣称 GUI 完整流程通过验收。

## OMP 历史回退能力核实（2026-09-24）

本轮仅核对 OMP v18.3.0 源码与文档，没有运行回退实验，也没有核实其他产品是否具备相同能力。

- [rewind 工具文档](https://github.com/can1357/oh-my-pi/blob/v18.3.0/docs/tools/rewind.md)描述的是探索上下文收束并保留报告，明确不恢复文件、进程或 Git 状态；它与用户选择历史消息回退的交互不是同一入口。

- 接入原则：优先复用原生行为；若桌面接口不足，补充暴露原生能力的适配，不自行扩展回退语义。GUI 应准确表达实际效果，不能把会话回退标为文件回滚。

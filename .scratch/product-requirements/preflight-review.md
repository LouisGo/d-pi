# 前期设计审查及关闭记录

> 本文前半部保留审查当时发现；2026-09-25 用户七项答复后的落实与当前状态见末尾「修订关闭记录」。不要把历史待办重新当成未讨论事项。

## 范围与方法

基于 HEAD `a56ea59504dfc03c29d3dd97155a3ced3c55bde5` 加审查时的工作区内容（包括未跟踪文档），不能只用 git diff 的六个已跟踪文件代表全部设计。核对现行需求、foundation、选型/Composer 研究、决定登记、CONTEXT、两个 ADR、diagnostics、README/handoff、三个验证报告和历史阶段证据；并与旧架构稿中的相关契约对照。历史源码/实验按相关问题抽查，没有重新运行，也没有对全部归档代码做产品审计。

采用独立的需求符合性与架构合同审查，再核实去重。个人记忆库未找到可用于补全本项目决定的条目；本次不依赖模糊记忆扩展用户要求。没有修改任何既有决定/规格，没有实现、安装依赖、重跑 Runtime、提交或推送；只新增本审查记录。

结论：无证据要求推翻 Electron/SessionHost/OMP 所有权、Monaco、D-20 或 D-21/D-22。此前“只剩三项”的概括过于乐观：它是主题归并，不代表基础合同已完成。以下是设计/接入缺口，**不是声称新应用已出现运行 bug**。

## A. 已有记录仍存在继承遗漏，先纠正而非再选型

### A1. 子 Agent 默认模型与档位的 GUI 设置未进当前总表

证据：[Settings 记录](../../docs/validation/settings-feasibility.md)第 3、11、40、51 行明确用户需求与限定实测：按 Agent 定义配置模型/档位，由主 Agent 正常创建，后续 spawn 生效。当前需求能力表与决定登记没有单列，foundation V1-06 只有观察。

影响：后续 AI 容易只实现观察，再把已讨论的配置能力当新需求。应补回最终需求索引，保留后续 spawn、非运行实例热切换的边界；是否首版另定，不重复询问“是否需要”。

## B. 产品骨架前应收敛的七组问题

### B1. Thread / 原生会话 / 实例 / 工作目录身份与生命周期

证据：[CONTEXT](../../CONTEXT.md)第 7 行明确持久映射待设计；[架构](../../docs/prototype/v1-architecture-draft.md)第 8、36–37 行要求进程映射、禁止双写且会话路径不等于已落盘；foundation V1-03/V1-09 要求并行与恢复。

触发：新 Thread 尚未产生原生文件，进程退出；重复打开历史会话；App 重启；CLI 占用；后续分叉或目录迁移。没有稳定映射会影响草稿、历史、恢复和所有 trace 关联。

建议先写最小模型和状态表：App Thread ID、原生 session reference、工作目录身份、Runtime 实例代次、创建中/可恢复/失效；集中持久化及原子写；App 内单写拥有者；原生锁能否跨 CLI 共用需核查，不能用本地 mutex 冒充跨程序互斥。

沿用一个 Host 管多个 OMP 基线，写清单实例与 Host 故障影响范围、关闭窗口与退出的状态转换、待交互/排队/后台活动如何结束，以及残留进程处理。不改已定关窗继续，不假定 abort 后所有活动已停止。

**责任：工程设计先做。** 只有 CLI 既有会话的导入体验、无法确认占用时是否继续等产品分支需要具体对齐。

### B2. 发送已接受但 ACK 丢失：不重试还不足以保证不丢输入

证据：foundation 第 61–62、69 行；架构第 29 行；[diagnostics](../../docs/architecture/diagnostics.md)第 53、61 行。当前定义结果未知后重同步，但未证明能识别“哪一次输入被接受”。已检查固定 v18.3.0 RPC 类型有请求 id 和 queuedMessageCount，不能据此推导持久幂等键或完整逐条接收账本。

触发：OMP 接受后 Host 崩溃，Renderer 没收到回执；重开后用户再次发送相同文字。相同文字可合法多次提交，不能用文本比对去重；trace ID 不是 Runtime 幂等保证。

建议定义 App submission 状态和有限持久收据元数据，核实原生队列/历史可重建范围。确实不能判定时保留 unknown 和原提交内容，提供核对后重发路径；不能自动重发，也不能偷偷清空草稿。只维护提交交接，不建立第二套 Agent 执行历史。

**责任：工程调查和输入状态合同。** 无法消歧的用户呈现应明确说明，不包装成 exactly-once。

### B3. 原生环境复用与全部供应商入口：初始化仍有真实接入风险

证据：[ADR-0002](../../docs/adr/0002-share-native-omp-config.md)第 13–17、33–35 行；foundation 第 42–44 行；[随包验证](../../docs/validation/packaged-runtime-evidence.md)使用受控 PATH/临时配置，没有验证真实用户 Finder 环境与 GUI 认证。

需要分开处理：

1. 配置上下文来源：cwd、配置根、profile、环境变量及其来源。不能把无法发现原环境当成确实无配置而新建另一套。
2. 包内版本与外部 CLI/项目配置兼容：不兼容时禁止不明格式写入；允许用户在 GUI 选择已有配置上下文，而非强迫重新认证。共享配置的跨进程并发写、record 更新需核查原生保证，App 内串行不能自动覆盖外部 CLI。
3. 按认证机制建接入矩阵：原生配置可用、GUI 新增/更新、OAuth 回调/秘密输入/本地与自定义服务、取消与失败。模型不设白名单不等于各认证路径已有可调用 GUI 接口。

不能简单恢复未验证 Bun ConfigHelper 为既定方案，也不能只写“薄适配”而不核实运行/打包边界。对缺口优先复用原生结构化接口/可维护扩展，若必须修改或长期 fork Runtime，再携证据请用户取舍。用户说“不管 OMP 内部日志”不等于禁止观测其错误，也不等于已授权维护 fork。

**责任：先技术调查。** 无感路径失败后的 GUI 修复方式及重大兼容降级才需用户决定；不重新讨论品牌白名单。

### B4. 高质量输入需要完整内容管线，不能只定 Composer

证据：foundation V1-04、第 59–70 行；[spec](spec.md)输入与引用待决项。结构化节点和引用 ID 已有建议，但尚未闭合：源文件改名/删除后附件是否仍可发送、重启后的内容引用、@ 文件与选区捕获时点、转换产物与原件保留/清理，以及 PDF/模型能力不匹配时的转换路径。

触发：拖入 PDF 后关闭 App；排队期间源文件被 Agent 修改；重新打开草稿时原文件消失；模型只支持文字而附件含扫描页或图表。只保留路径不等于冻结内容，只抽取文字不等于完整保留图像语义。

建议先统一业务内容包、原件/派生内容/引用来源及版本、准备/失败/可提交状态、生命周期与容量上限。优先复用 OMP，不能默默换模型、送外部解析服务或截断内容。常规实现由工程决定；任何信息损失或付费/外部传输取舍显式呈现。

**责任：工程方案为主，核心产品默认行为需随方案确认。** 不能让 ProseMirror 选型遮盖这条管线。

### B5. 宿主权限与原生审批的职责没有正式对上

证据：foundation 第 122 行引用“产品权限规则”，但现行文档没有对应规则；diagnostics 第 60 行只说明 trace 不是权限凭证。历史安全基线需继承，但仍需要把新文件/附件能力映射进去。

触发：拖入项目外文件、symlink 越界、模型输出包含路径、Renderer 发错 Thread 的绝对路径，以及 Side Chat 后续声称只读但拥有可写工具。

建议最小能力表：用户选择项目/附件分别授予哪些读取范围；工具输出路径只作数据；宿主检查调用来源、Thread/资源归属与路径解析；OMP 工具执行/审批继续由其原生机制负责，GUI 不默默覆盖；只读能力应在工具/接口层限制，不能仅靠 prompt。核实“打开项目”与“启动执行”何时会加载扩展或执行配置逻辑。

**责任：先调查并给出工程边界，不默认新增沙箱或复杂审批平台。** 只有原生行为与用户期望冲突时再讨论体验取舍。

### B6. 有界输出与无感诊断需要可重建清单和测量标准

证据：架构第 27–28 行；foundation V1-06/V1-07；diagnostics 第 140–145、175–177 行；Runtime 验证说明子 Agent 终态退出活动列表、历史枚举完整性未测。

触发：后台运行数小时、工具输出很长、子 Agent 结束后再打开窗口、Renderer 更新慢。无限保留不成立，盲目丢弃后也不一定能从原生历史恢复；日志是诊断，不是业务恢复数据库。

建议按事件分清可合并、必须保序、可重读、必须暂存的内容；定义快照水位、历史分页/瞬态事件恢复、容量与缺口表达。对 diagnostics 明确默认关键事件与 debug 采样、关键链路保留、脱敏来源、队列/磁盘预算与异常退化。

日志整体设计已较完整，无需再加平台；缺的是以首版真实负载定义验收样本/预算并在获准技术验证后测量。不能提前编造性能数字，也不能无限期用“待实测”替代验收门槛。没有数值基线前只可标设计就绪，不可标性能通过。

**责任：技术合同和验证。** 用户不需要选择队列实现或日志库。

### B7. “首版”与“第一次内部可运行里程碑”仍混在同一清单

证据：foundation 第 15、20–31 行明确 proposed，一次纳入新用户初始化、多 Thread、全附件；第 36 行将内置 worktree 创建和历史操作后排。D-06 只确定主对话/只读/Diff 方向，D-20/21/22 的确认没有批准整张首版清单。

这些安排不是错误，但总工作量与用户最早能试用的时间有很大区别。必须明确对外验收与内部开发顺序，避免“先全部建设才能运行”重新出现。

建议维持完整目标，区分：内部验证闭环（已有可用配置、真实任务、输入/恢复/日志/只读Diff）→ 首版验收集合（按确认范围补新用户、多Thread、全部必要输入）→ 后续能力。没有确认前不擅自把新用户/附件从首版移除，也不把每项都升级为第一次可运行的前置。

**责任：需要用户认可阶段定义和最终首版范围；工程先给具体方案，不重开已确认能力。**

## C. 真正需要继续沟通的内容

不是把 B1–B7 变成七个开放问题。工程先处理身份/恢复、提交交接、认证接入矩阵、内容管线、宿主能力、输出与性能等合同。与用户的下一次沟通集中在：

1. 最早内部验证与首版交付的区别，特别是新用户初始化、全部附件和多 Thread 的批次；不降低最终目标。
2. 既有 CLI 配置无法自动识别或版本不兼容时，允许在 GUI 明确选择/修复上下文，不覆盖、不暗中另建配置。标准可用路径保持零配置。
3. 内容或操作结果不能无损/确定处理时，界面必须准确说明；具体降级、外部服务或 Runtime 维护成本只有拿到证据后再讨论，不现在要求用户选假想方案。

ProseMirror 暂保持推荐而非已验收；同目录并行保持允许，但恢复旧有共享关系提示，不默认强制 worktree。仅当需要限制并行、自动串行化或扩大授权时才是新产品决定。

## D. 后续阶段可留待细化的内容

完整 Run Changes / Review / Revert、Side Chat 上下文同步和运行中模型切换、浏览器 computer use 页面策略、终端高级生命周期、完整语言服务、Git 进阶操作、专用诊断 UI，继续按对应阶段处理。保留数据身份与接口边界即可，不提前实现它们。

发行签名/公证、Intel/其他系统支持、更新/回退安装器的具体实现可在分发阶段细化；包内 Runtime/共享配置的数据兼容原则则须在首次持久写入前明确。没有既定发行范围，不将当前开发机可运行当可公开分发。

## E. 文档与记忆的保全

决定登记/AGENTS 是规则，不是防误改的自动保证；当前核心新文档仍未跟踪，恢复工作也未提交。正式实施前应形成一次经审阅的 Git 基线，保留已确认/提议的状态；本轮没有获得提交/推送指令，未执行。

后续规格应引用决定 ID 与唯一详细合同，避免多处复制不断积累不同版本。按“需求/决定 → 合同 → 验收场景 → 证据”追踪，已有实验只证明其固定范围。审查问题可在修订时按本报告 ID 逐条关闭，不能把生成本报告当成已解决。

## 完成判断

当前是**方向可继续、详细合同待补齐**，不是需要推翻重来，也不是正式产品骨架已具备全部前提。下一步应补最小基础合同、同步遗漏的历史决定，完成有边界的设计审阅；获准进入技术验证后，用隔离样本验证无法靠讨论证明的接口/输入/性能，再启动正式实现。不能承诺仅靠继续聊天实现零返工。

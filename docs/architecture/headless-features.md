# 验证先行的无头功能与应用生命周期

日期：2026-09-25。状态：用户已确认的架构方向，具体模块随功能验证与实现确定。依据 D-28–D-30；延续 D-02 的进程所有权、D-21/D-22 的诊断及 D-24–D-26 的[基础契约](foundation-contracts.md)。本次只沉淀文档和仓库 skill，不启动产品、交互原型或依赖安装。

## 1. 按功能推进：验证 → 无头功能 → 正式 GUI

以最小成本验证可能改变产品承诺、数据正确性或接入路线的问题，再实现可独立验证的功能模块，最后接入正式 GUI。组件化包括规则、流程、状态投影、查询和外部接入的组合，不只指视觉组件。

| 步骤 | 交付 | 完成证据 |
| --- | --- | --- |
| 能力验证 | 有边界的实验、接口事实、失败行为与未覆盖项 | 固定版本/场景的可复现结果；已足够的历史证据直接复用 |
| 无头功能 | 当前场景所需的契约、规则、状态转换及副作用接入 | 不挂载 React 即可验证业务路径；真实接入与故障样本覆盖关键合同 |
| 正式 GUI | 薄 React 接入、交互与视觉组件、页面组合 | 真实 Electron 用户路径、输入/阅读/焦点与性能验收 |

这是每个功能内部的顺序，不要求先完成全产品的验证或全部逻辑。G1 为对应功能的门槛，M1/M2 仍需交付可用 GUI，M3 保持后续能力集合。无头功能通过不能冒称 M1/M2 完成。

正式视觉设计与高保真图在对应功能契约得到验证后开展；前期仍要明确用户意图与操作场景。IME、焦点、编辑器选择、滚动等可用最小无样式界面提前实验，不先建设正式页面，也不把 UI 专属风险全部拖到最后。获得对应阶段授权后才执行实验或实现。

## 2. 中间层也要分职责

| 职责 | 所有内容 | 边界 |
| --- | --- | --- |
| 功能规则与状态转换 | 提交条件、草稿版本、冻结内容、恢复规则等；复杂状态用 TypeScript 联合类型与显式转换 | 不依赖 React、DOM、组件库；不重新实现 OMP 执行循环 |
| 功能协调与外部接入 | 调用原生能力、存储与内容处理；关联结果、处理取消/失败、转换为应用合同 | 副作用通过明确接口接入；在既定 Main/Host/Renderer 边界内安排，不建万能服务 |
| 状态投影与查询 | 可订阅的客户端视图数据、派生选择器、异步查询缓存 | 一个数据事实一个权威拥有者；缓存/镜像不是第二份 OMP 历史 |
| React 接入与无头交互 | 选择性订阅、调用功能操作、编辑器/焦点等视图资源绑定 | hooks 是接入方式，不是所有功能的容器；无样式不等于不依赖 DOM |
| 视觉组件与页面 | 布局、样式、动画、可访问性及操作入口 | 通过功能 API 读取与操作，不直接解析 OMP 协议或改业务状态 |

以上是职责，不要求为每项建包、类或独立进程。按功能组织紧密相关代码，借助显式依赖组合协作；不先建继承体系、通用 BaseManager、插件平台、全局事件总线或 DI 容器。简单函数和参数传入足够时就采用它们。

核心依赖业务接口；外部适配实现接口并在应用启动/对应作用域创建时组装。生产接真实接口，测试接可控实现。Renderer 只能使用受限客户端接口，不能借依赖注入获得 Node/文件系统权限。协议校验与资源授权继续在可信宿主执行。

## 3. 生命周期先于 hooks 选择

这是持续运行的桌面应用，不按 Web 页面路由挂载/卸载决定业务存活。为每个有状态模块明确创建者、作用域、销毁条件和恢复来源。

| 作用域 | 典型资源与拥有者 | 结束条件 |
| --- | --- | --- |
| 应用/宿主 | Main 监督与集中存储，Host 的 OMP 连接和协议投影 | 应用退出或所属进程故障；按基础契约恢复 |
| Thread/工作目录 | Thread 提交关联、内容准备；按需共享的工作目录资源 | 显式结束/删除或满足回收条件；切换前台不等于结束 |
| Renderer 连接 | 本窗口客户端连接、展示镜像、查询缓存 | 窗口/连接销毁；重开从宿主与持久数据恢复 |
| 具体视图 | 订阅、DOM 监听、编辑器实例及焦点资源 | 对应视图卸载；应释放视图资源，不顺带停止任务 |

应用级不等于一个全局可变单例。按 Thread、工作目录和连接身份隔离实例；有共享资源时明确拥有者与释放规则。多个视图可以订阅同一实例，订阅不能隐式发起两次任务；最后一个订阅者离开也不能自动取消需后台继续的工作。

hooks 可以绑定或获取已有功能实例、订阅数据和管理视图专属资源；不得在组件 effect 中拥有 OMP 进程、持久提交、共享队列、后台附件任务等业务生命周期。视图发起的取消订阅与显式取消业务操作是两种动作。异步返回仍按 Thread、提交身份、实例代次与版本验证，不能只靠 isMounted 防止串线。

## 4. 对外合同与状态工具

功能 API 表达业务意图、可用操作及原因、结果和可订阅状态，不暴露任意写状态的入口，也不绑定 Toast、弹窗或按钮。权限和状态前置条件由操作执行方复核，不能仅靠 disabled 按钮保证。具体接口只覆盖当前已确认场景，不追求任意未来 UI 都零修改。

例如提交功能组合内容准备、收据存储与 Runtime 入口，暴露“提交/恢复内容”等操作和提交状态；按钮、快捷键、测试脚本复用同一规则。失败后如何排版由视图决定，保留原提交且不覆盖新草稿由功能合同决定。编辑器选区、IME 与撤销仍由编辑器机制拥有，通过业务 DTO 对接草稿与冻结内容。

- **不引入 XState。** 状态转换采用 TypeScript 的明确模型、纯函数或局部协调模块，不借此自研通用状态机框架。
- **Zustand** 承载客户端展示状态与细粒度订阅，可用 vanilla store 与 React 接入分离；不成为后台执行或原生历史的权威拥有者。
- **TanStack Query** 承载模型、配置摘要、历史目录等异步查询缓存；查询函数与 key 可以独立于 hooks 组织。同一可变正文不在 Query 和 Zustand 双写，不用查询重试机制自动重发结果未知的副作用。
- **React hooks** 连接功能与视图；不把业务函数仅因“复用”改成 hook，不用多个 effects 隐式拼装业务状态机。

纯函数处理规则与状态转换，文件、IPC、时钟等副作用通过窄接口集中协调；无头不等于所有函数无副作用。不为换状态库方便而给每个工具再套一层通用框架。

## 5. 验收与性能分层

按当前功能选择必要验证，不要求每张票重复全套：

- 不挂载 React 可验证关键规则和完整业务交接；可控接口覆盖拒绝、迟到、断链和存储失败。真实 OMP 集成证据与模拟样本分开。
- 两个视图/订阅者不会重复启动任务；卸载视图不终止后台业务；重挂载和 Thread 切换不串状态。作用域销毁后相关监听、计时器与资源释放。
- 使用相同事件样本检查序号、旧代次、内容冻结和恢复；复用样本到后续组件验证，不用测试脚本取代正式业务规则。
- 无头层测事件处理、背压、内存、取消与订阅通知成本；按实体/block 订阅，避免每个 token 更新整项任务的所有消费者。诊断从第一条链路接入，预算沿用基础契约，不编造已达标结果。
- GUI 接入后另测真实 IME、渲染、选择、滚动与响应延迟；换组件库不应修改提交/恢复/权限规则，但视图集成和性能仍须重新验收。

## 6. 任务拆分

以一个可验证行为为单位；每票写明阶段、受影响决定、交付结果、依赖、关键拥有者/生命周期及验收证据。规则详见[本地 issue 约定](../agents/issue-tracker.md)。

验证票交付事实和结论，无头票交付可执行功能与测试，GUI 票消费已验证合同并验收用户路径。可在一个小任务中依次完成，也可按真正依赖拆票；“纵向切片”不强制每张无头票都带正式 GUI。避免拆成全局的“所有 store → 所有 hooks → 所有页面”，也不把一个按钮或一个类型默认作为独立任务。

to-tickets 在当前功能范围和所需证据足够明确后用于拆票，不替代验证或决定产品范围；先细化最近的 G1/M1，远期不提前拆成大量实现票。用户只要求文档时，不据此发布整套任务或开始编码。

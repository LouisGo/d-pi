# 证据优先的无头功能与应用生命周期

日期：2026-09-25；2026-09-27 按用户反馈调整验证投入，2026-09-28 补 TDD 与自动化优先。状态：用户已确认的架构方向，具体模块随功能实现确定。依据 D-28–D-30；延续 D-02 的进程所有权、D-21/D-22 的诊断及 D-24–D-26 的[基础契约](foundation-contracts.md)。实施授权和当前进度以近期 spec/交接为准；本合同不自行授权新切片。

## 1. 按功能推进：验证 → 无头功能 → 正式 GUI

这里的“验证”首先是查证已有事实，不是默认搭实验。先用官方文档、固定版本源码及已有项目证据回答当前问题；资料足够时直接实现功能模块，再接入正式 GUI。仅关键未知需要最小前置实验。组件化包括规则、流程、状态投影、查询和外部接入的组合，不只指视觉组件。

| 步骤 | 交付 | 完成证据 |
| --- | --- | --- |
| 证据核对／必要时验证 | 当前能力依据与仍会改变实现选择的关键未知 | 官方文档、对应版本源码或已有证据即可；只有资料不足的关键未知才补最小实验 |
| 无头功能 | 当前场景所需的契约、规则、状态转换及副作用接入 | 不挂载 React 即可验证业务路径；真实接入与故障样本覆盖关键合同 |
| 正式 GUI | 薄 React 接入、交互与视觉组件、页面组合 | 当前改动的真实用户路径与体验交接；性能专项按风险和里程碑安排 |

这是功能职责与推进顺序，不是每个功能固定三张票或三轮检查。G1 只约束对应功能尚未回答的关键风险，M1/M2 仍需交付可用 GUI，M3 保持后续能力集合。无头功能通过不能冒称 M1/M2 完成。

正式 GUI 在当前契约和关键风险已有足够依据后开展，不必等独立实验报告；前期仍要明确用户意图与操作场景。IME、焦点、编辑器选择、滚动等可用最小无样式界面提前实验，不先建设正式页面，也不把 UI 专属风险全部拖到最后。按当前任务授权执行；一次完整功能实现授权包含其必要验证、修复与 GUI 接入，无需按这三个步骤重复确认。文档/调查请求不据此扩为实现。

### 验证选择与停止条件

| 当前情况 | 默认做法 |
| --- | --- |
| OMP 官方已描述的能力、成熟库的常规用法、项目已有适用结果 | 核对相关版本/接口并在任务中简记来源后实现；不重复证明库能用，不建立“可行性探针”前置 |
| 一般接入细节或可逆局部选择 | 在真实实现中检查并修复；正常类型/lint、针对性行为测试或一次相关 GUI 操作即可，不先复制一套实验实现 |
| 资料不足且会影响架构/产品承诺，或存在数据丢失、权限/不可逆副作用、特殊平台/原生运行环境风险 | 先写清未知问题、受影响选择、最小样本和停止条件，再做有界实验；既有证据已经回答的部分不重做 |
| 发现实际失败、关键路径变更或进入里程碑组合验收 | 围绕影响补回归、故障或性能检查；不自动扩为全产品全矩阵 |

官方来源、源码事实、模拟与本应用实测分别标明，不把一层证据冒充另一层。普通能力无需为了“没有实测”阻塞实现，但提交结果未知不能自动重发、存储不能静默丢数据、权限不能虚报等合同仍必须由本应用正确落实。

实验只回答事先指出的关键未知；答案足以支持下一步即停止，不为凑齐指标、报告或三阶段形式继续扩样。每次复测应能指出新增改动、失败或尚未解决的问题。已通过基线仅在依赖/接口/配置/运行环境或相关代码变化使其失效时重做受影响部分，不因切片编号改变重跑。

前置可行性、实现正确性、用户体验是不同问题。减少前置实验不免除必要测试，也不允许把测试当用户认可；每段可操作体验仍及时交给用户。S1 的 Markdown 原文粘贴缺陷说明应优先核对具体输入/输出合同，而非用更多通用库探针替代产品行为检查。

### TDD 与自动化优先（2026-09-28）

用户明确调整：TDD 优先；Computer use 只用于原生系统交互、视觉体验等难以替代的少量检查，或用户明确要求。此规则细化 D-28，取代将“真实 GUI 验收”解释为每次必须用 Computer use 的做法；不改变产品范围、必要集成检查与用户试用边界。

- 功能/缺陷修复逐行为执行红 → 绿 → 按需重构。先运行失败测试，确认因目标行为缺失而失败，再写最小实现；不一次铺完所有测试再批量实现。有可用 `tdd` skill 时沿用其方法，缺少该全局 skill 也按本节执行，不将安装设为前置。
- 既有行为补测是回归覆盖，不伪称此前执行了 TDD，也不故意破坏正确实现制造开发红灯。关键测试可用少量针对性变异验证能否拦截真实回归；变异验证与开发红灯分别记录，立即恢复临时改动。
- 测试通过公开行为边界，断言用户/调用方可见的结果。优先真实业务协作与临时 SQLite；只在 IPC、时钟、系统编辑器等外部边界用替身。避免私有字段、内部调用顺序、常量复述、无意义快照和以数量/覆盖率为目标。
- 业务规则与协调优先 Vitest；DOM/组件交互按需用组件测试；稳定跨进程用户流程按需用可重复 E2E。只为具体缺口增加工具，不预建整套测试平台，不在每次任务同时跑全层矩阵。
- Computer use 补自动化难以替代的原生 IME/系统窗口或视觉体验证据，或响应用户明确要求。使用前简述具体未知与停止条件；不能因已有“GUI 验收”字样就重复点击已被自动测试覆盖的流程。普通场景无需反复向用户询问是否使用。
- 自动测试通过不等于真实 IME/视觉验收或用户认可；未检查的层级如实保留。所需证据足够即交付，不机械重跑历史包、性能或故障矩阵。

### 日常改动的验证选择（2026-10-07）

沿用 D-28，按受影响行为、失败后果和已有证据选择验证；代码行数或是否有 GUI 不是风险等级。下表是默认选择，不覆盖当前用户明确要求或所属票已声明的必要验收。

| 改动范围 | 默认选择 | 何时增加验证 |
| --- | --- | --- |
| 文档、注释、工作记录 | 相关文档/状态检查与 diff 核对 | 涉及可执行命令、配置或检查入口时验证对应行为 |
| 局部样式、布局、控件状态 | 相关 lint；针对性的浏览器视觉或交互检查 | 真实渲染、焦点、原生窗口等问题仍未被证明时补对应证据 |
| 业务规则、状态协调 | 受影响的行为测试与类型检查 | 改到组件或跨进程接线时补相关集成场景 |
| IPC、存储、执行与资源生命周期 | 行为测试与受影响的集成场景 | 风险必须依赖真实 Electron/SDK 或包内资源才能证明时升级到该层 |
| 打包、运行时资源、里程碑组合交付 | 受影响的包内验证或组合验收 | 只按接口、资源、环境变化或实际失败扩大范围 |

运行高成本 E2E、原生包或 Computer use 前，在现有任务记录或进度说明中用一句话说明：当前未被证明的风险、较低层证据为何不足、这次场景及停止条件。没有具体证据缺口时不升级；Computer use 不重复已由真实浏览器自动操作回答的流程。完整检查可用于集成/CI，不能据此要求每次编辑都先跑完整 E2E。

复用基线时记录原证据及其仍适用的依据；共享 CSS 按受影响控件验证，未改变执行/存储合同不自动重跑供应商、冷恢复等业务矩阵。新的 source commit 或打包哈希本身不使所有历史行为证据失效，也不能将历史证据标为新构建复测。通过后只因新增改动、相关失败或仍未解决的重要风险复测受影响部分。

场景命令、默认完整入口与覆盖限制见[工程入口](../engineering/checks.md#按场景运行-gui-验证)。验证驱动修改要证明选择范围确实生效、错误选择失败、原完整路径仍可运行；不因为它使用 Electron 就再机械增加人工点击层。

## 2. 中间层也要分职责

| 职责 | 所有内容 | 边界 |
| --- | --- | --- |
| 功能规则与状态转换 | 提交条件、草稿版本、冻结内容、恢复规则等；复杂状态用 TypeScript 联合类型与显式转换 | 不依赖 React、DOM、组件库；不重新实现 OMP 执行循环 |
| 功能协调与外部接入 | 调用原生能力、存储与内容处理；关联结果、处理取消/失败、转换为应用合同 | 副作用通过明确接口接入；在既定 Main/Host/Renderer 边界内安排，不建万能服务 |
| 状态投影与查询 | 可订阅的客户端视图数据、派生选择器、异步查询缓存 | 一个数据事实一个权威拥有者；缓存/镜像不是第二份 OMP 历史 |
| React 接入与无头交互 | 选择性订阅、调用功能操作、编辑器/焦点等视图资源绑定 | hooks 是接入方式，不是所有功能的容器；无样式不等于不依赖 DOM |
| 视觉组件与页面 | 布局、样式、动画、可访问性及操作入口 | 通过功能 API 读取与操作，不直接解析 OMP 协议或改业务状态 |

以上是职责，不要求为每项建包、类或独立进程。按功能组织紧密相关代码，借助显式依赖组合协作；不先建继承体系、通用 BaseManager、插件平台、全局事件总线或 DI 容器。简单函数和参数传入足够时就采用它们。

核心依赖业务接口；外部适配实现接口并在应用启动/对应作用域创建时组装。生产接真实接口，测试接可控实现。Renderer 只能使用受限客户端接口，不能借依赖注入获得 Node/文件系统权限。协议校验与资源授权继续在可信宿主执行。

## 3. 生命周期先于 hooks 选择

这是持续运行的桌面应用，不按 Web 页面路由挂载/卸载决定业务存活。为每个有状态模块明确创建者、作用域、销毁条件和恢复来源。

| 作用域 | 典型资源与拥有者 | 结束条件 |
| --- | --- | --- |
| 应用/宿主 | Main 监督与集中存储，Host 的 OMP 连接和协议投影 | 应用退出或所属进程故障；按基础契约恢复 |
| Thread/工作目录 | Thread 提交关联、内容准备；按需共享的工作目录资源 | 显式结束/删除或满足回收条件；切换前台不等于结束 |
| Renderer 连接 | 本窗口客户端连接、展示镜像、查询缓存 | 窗口/连接销毁；重开从宿主与持久数据恢复 |
| 具体视图 | 订阅、DOM 监听、编辑器实例及焦点资源 | 对应视图卸载；应释放视图资源，不顺带停止任务 |

应用级不等于一个全局可变单例。按 Thread、工作目录和连接身份隔离实例；有共享资源时明确拥有者与释放规则。多个视图可以订阅同一实例，订阅不能隐式发起两次任务；最后一个订阅者离开也不能自动取消需后台继续的工作。

hooks 可以绑定或获取已有功能实例、订阅数据和管理视图专属资源；不得在组件 effect 中拥有 OMP 进程、持久提交、共享队列、后台附件任务等业务生命周期。视图发起的取消订阅与显式取消业务操作是两种动作。异步返回仍按 Thread、提交身份、实例代次与版本验证，不能只靠 isMounted 防止串线。

## 4. 对外合同与状态工具

功能 API 表达业务意图、可用操作及原因、结果和可订阅状态，不暴露任意写状态的入口，也不绑定 Toast、弹窗或按钮。权限和状态前置条件由操作执行方复核，不能仅靠 disabled 按钮保证。具体接口只覆盖当前已确认场景，不追求任意未来 UI 都零修改。

例如提交功能组合内容准备、收据存储与 Runtime 入口，暴露“提交/恢复内容”等操作和提交状态；按钮、快捷键、测试脚本复用同一规则。失败后如何排版由视图决定，保留原提交且不覆盖新草稿由功能合同决定。编辑器选区、IME 与撤销仍由编辑器机制拥有，通过业务 DTO 对接草稿与冻结内容。

- **不引入 XState。** 状态转换采用 TypeScript 的判别联合、纯函数或局部协调模块；D-35 确认 ts-pattern 为业务分支默认范式，Zod v4 负责边界解析，详见[TypeScript 合同](typescript.md)。不借此自研通用状态机框架。
- **Zustand** 承载客户端展示状态与细粒度订阅，可用 vanilla store 与 React 接入分离；不成为后台执行或原生历史的权威拥有者。React 绑定统一用官方 `useStore(store, selector)`；模型只暴露只读的 store 视图，`getState`/`getSnapshot` 留给无头读取与测试。
- **选择器快照保持稳定。** 原始值或 store 内已有引用直接选择；派生数组/对象用 `useShallow`、记忆化或预计算，使未变化结果保持引用。直接写 `useStore(store, (state) => ({ busy: state.busy }))` 会每次返回新对象，可能触发 `getSnapshot should be cached` 并进入无限重渲染。列表更新保留未变化实体引用，热路径同时评估查找和通知成本，不能只凭少渲染宣称低成本。
- **TanStack Query** 承载模型、配置摘要、历史目录等只读异步查询缓存；查询函数与 key 可以独立于 hooks 组织。同一可变事实不由 Query 与 Zustand 独立双写。允许同一 Thread 的历史分页与实时尾部保留范围明确的投影；重叠时按领域身份与版本合并、去重，不成为两份可独立修改的正文权威。历史分页随对应功能接入，不提前扩展范围。
- **执行命令保持原拥有者。** 发送、回答、停止、继续沿用协调器与收据合同，不进入 Query 的缓存、重试或恢复机制去自动补发。这是 D-24/D-29 的项目政策，不是声称所有 Mutation 配置都必然重试或重发；保存等既有写操作也不因接查询库搬走事务和写入职责。
- **本地读取的网络语义**（本节是这条规则的单源）：桌面端文件、Git 与配置查询不经网络，一律显式 `networkMode: 'always'`，不因 Renderer 判定离线而暂停；返回值中的 `unavailable`（非 Git/缺失/拒绝/二进制/超限/变化中等）是业务结论而非可重试错误，只有采样失败才走默认重试。刷新是显式动作，不做定时轮询；查询缓存不是磁盘或 Git 真相，缓存命中不伪报成功。各模块页只描述自己的 key 与结果，不重复这条规则。
- **TanStack Router** 仅在 `app/renderer` 表达导航目标、阅读页签与内存历史（D-38）；Main 的 Thread 选择和 AppModel 的资源生命周期保持权威。导航先经编辑冻结、草稿 flush 和选择确认，失败不提交路由；preload/loader 不执行命令。完整接入合同见[应用导航](navigation.md)。
- **React hooks** 连接功能与视图；不把业务函数仅因“复用”改成 hook，不用多个 effects 隐式拼装业务状态机。

纯函数处理规则与状态转换，文件、IPC、时钟等副作用通过窄接口集中协调；无头不等于所有函数无副作用。不为换状态库方便而给每个工具再套一层通用框架。

## 5. 验收与性能分层

以下是按风险选取的检查样本，不是每功能必跑清单。默认查证据后实现，复用现有基线；正常检查够用时不搭专用测量工具。完整性能/故障组合用于 M1/M2 对应验收，日常只覆盖受影响项：

- 不挂载 React 可验证关键规则和完整业务交接；可控接口覆盖拒绝、迟到、断链和存储失败。真实 OMP 集成证据与模拟样本分开。
- 两个视图/订阅者不会重复启动任务；卸载视图不终止后台业务；重挂载和 Thread 切换不串状态。作用域销毁后相关监听、计时器与资源释放。
- 使用相同事件样本检查序号、旧代次、内容冻结和恢复；复用样本到后续组件验证，不用测试脚本取代正式业务规则。
- 无头层测事件处理、背压、内存、取消与订阅通知成本；按实体/block 订阅，避免每个 token 更新整项任务的所有消费者。诊断从第一条链路接入，预算沿用基础契约，不编造已达标结果。
- GUI 接入后检查受影响的输入、渲染、选择或滚动路径；只有改动触及性能热点、出现退化或进入专项验收才测响应延迟。换组件库需要检查受影响集成，不默认重跑所有性能样本。

以一个可验证行为为单位；每票写明阶段、受影响决定、交付结果、依赖、关键拥有者/生命周期及验收证据。规则详见[本地 issue 约定](../agents/issue-tracker.md)。

默认在功能票内引用已有证据并完成实现和必要检查；只有独立的关键未知值得跟踪时才拆验证票。无头票交付可执行功能与测试，GUI 票消费有依据的合同并验收用户路径。可在一个小任务中依次完成，也可按真正依赖拆票；“纵向切片”不强制每张无头票都带正式 GUI。避免拆成全局的“所有 store → 所有 hooks → 所有页面”，也不把一个按钮或一个类型默认作为独立任务。

在当前功能范围和所需证据足够明确后，按本地 issue 约定拆票；可选工具不能替代验证或决定产品范围，也不是开始工作的依赖。先细化最近的 G1/M1，远期不提前拆成大量实现票。用户只要求文档时，不据此发布整套任务或开始编码。

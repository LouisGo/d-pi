# 开发基础契约

制定：2026-09-25；2026-09-26 按 D-33/D-34 更新 Composer 与 App 存储。依据：用户对审查 B1–B7 的逐项答复。B1/B2/B4 采纳建议，B3 限定首版认证入口，B5 要求简单权限选项，B6/B7 授权工程补齐与阶段划分。本文是据此确定的工程设计，**不是实现或实测结果**。决定索引见 [D-23 至 D-26](../decisions.md)，审查来源见 [preflight](../../.scratch/product-requirements/preflight-review.md)。数值为初始工程预算，可按测量记录调整，不属于用户逐项承诺。

## 1. 身份、持久化与生命周期（B1）

- `threadId` 为 App 生成的稳定 ID，创建草稿即分配，重启、换模型、OMP 重启不改变。`nativeSessionRef` 可空，仅在原生确认后绑定，包含配置上下文标识、原生 ID/路径；路径不是已经落盘的证明。没有落盘记录时保留 Thread 与草稿，恢复为未启动/中断，不伪造会话历史。
- `workingDirectoryId` 对应规范化工作目录及其关联项目；原目录与 worktree 独立标识。同目录多 Thread 明显提示共享文件，不强制串行。目录丢失/移动后暂停执行，由用户重新关联，不自动在同名目录继续。
- `processInstanceId`、`connectionGeneration` 每次实例/连接变化重新分配；过期回执不能更新新连接。原生分叉创建新的 Thread 与会话引用，保存父 Thread/原生条目关联；树内导航不新建 Thread。
- D-34：App 自有结构化数据采用 SQLite，包括 Thread/工作目录关联、草稿 revision、提交收据、内容引用及桌面偏好。Main 集中拥有持久化入口与写入调度，数据库连接留在可信宿主；Renderer/其他消费者走类型化功能接口，不直接打开库或覆盖整份数据。OMP 原生会话/配置仍由 OMP 写，不导入数据库另造原生历史或凭据副本。
- 草稿 revision、提交收据和内容引用中需要同时生效的更新使用数据库事务，写入前检查版本/状态前置条件；事务提交成功后才报告持久化成功或推进派发。附件原件/派生内容仍在私有文件存储，明确文件写入、数据库引用、派发、回执保存与 GC 的顺序及崩溃恢复；SQLite 事务不覆盖文件系统操作或 OMP 接受，不提供 exactly-once。
- schema 迁移带版本并可追溯；升级前提供可恢复备份，失败不删库重建，未知更高版本只读或停止不兼容功能，不静默降级/重置。按实际驱动验证事务持久性、外键约束、迁移与恢复；锁冲突/磁盘满/写失败返回明确错误，存储重试不能重发 OMP 操作。只读模式也必须通过版本兼容检查。
- SQLite 已定；具体驱动、是否配 Drizzle、journal/同步参数在持久化切片确定并记录。核实 Electron 内置 Node、原生模块 ABI、打包与支持平台，不直接照搬系统 Node 的能力。Main 不执行无界同步查询；如需 worker 承担 I/O，Main 仍集中拥有存储职责，不新增多方竞争写入。最小验证涵盖事务中断、迁移失败、重启恢复和文件/数据库引用不一致。
- 一个 utility SessionHost 管多个独立 OMP，一个活跃顶层会话一个 OMP。Main 监督 Host，Host 监督自己的 OMP；子 Agent 属于 OMP。单个 OMP 崩溃只中断其 Thread；Host 崩溃使所有所管连接中断。先确认并清理本次实例残留，再允许恢复，不能只靠 PID 杀进程或接回旧 stdio。
- D-40 用户集成终端另由专用 TerminalHost 承载 PTY/shell，Main 管准入与监督；不进入 SessionHost/OMP 故障域，不沿用 OMP 原生会话恢复。终端身份、显示重挂载、输出/清理及待决见[终端契约](terminal.md)与[所属规格](../../.scratch/integrated-terminal/spec.md)，当前仅文档设计。
- App 内同一原生会话只有一个执行拥有者，采用单 App 实例入口。**不声称已有跨 CLI 会话锁。** 首版执行恢复限于 App私有native-sessions、持有跨App生命周期lease并已确认旧已注册原生进程停止的记录；CLI 历史导入执行后排。固定OMP短publish锁不等于执行全周期锁，d-pi只对遵循其私有会话协议的启动入口持有真实互斥；无法确认占用时允许查看，阻止追加，提示关闭原运行入口后重查，不能自动强占。即便检测未发现冲突，也不能宣称可阻止不遵循锁的外部写入。

| 状态/动作 | 合同 |
| --- | --- |
| 浏览已有历史 | 不启动 Agent，不加载项目可执行扩展；只读历史解析与执行加载分离 |
| 开始/恢复任务 | 校验配置、目录、信任、会话占用后启动；未就绪不开放发送 |
| 关窗/刷新 | OMP 继续，后台仍消费输出；重开接快照再接增量 |
| 空闲回收 | 仅无执行、无排队、无待交互、无后台子任务且已持久化的实例可回收 |
| 等待退出 | 队列/待交互/后台活动算未完成；可返回窗口回答，保留取消退出入口 |
| 停止后退出 | 原生 abort 不等于清队列；检查实际终止，超时显示残留并提供明确强制结束，不能静默退出 |
| 崩溃 | 标记中断/提交结果未知；不自动重放输入或副作用，不把进程退出等同任务成功 |

运行中的停止入口分别呈现“已请求中断”、经证据确认的当前执行结果及仍待处理的输入/后台活动；abort 回执不能直接使整项任务显示“已停止”。M1 接入前用执行中工具、follow-up、steer、待回答交互的组合验证停止后的实际行为；队列状态无法确认时明确标未知。2026-09-27 用户确认停止的产品语义为：中断当前执行，同时暂缓当前 Thread 后续队列，保留排队内容，只有用户明确继续才允许恢复消费；取代此前仅观察原生 abort 结果、后续队列行为未定的方案。停止不回滚文件，也不以清空后自动重发来模拟暂停。队列暂缓必须在执行侧成立，验证中断与下一条消费的竞争；无法确认时显示未确认或失败，不能只改变按钮状态。该语义纳入 M1 控制接入验证，不把 M2 完整逐项队列管理一并前置。后台工具/子 Agent 的真实终止仍独立核实，不能据此宣称所有外部进程均已结束。

## 2. 提交交接（B2）

每次用户提交分配 `submissionId`，绑定 threadId、草稿 revision、冻结内容包、模式（普通/排队/干预），traceId 只用于追踪。Main 管最小持久收据，Host 负责 RPC 关联，OMP 负责接受后的真实执行/队列。

2026-09-28 用户明确选择“保留官方 OMP”，采用持久发送记录保护原文；取代此前“仅业务接受证据持久化后才能清稿”的条件。原决定沿革见 D-24，具体 S2 方案见 [S2 spec](../../.scratch/m1-s2-submit-read/spec.md)。这项变化不把通信成功重新定义为业务接受。

交接主路径：`preparing → prepared → dispatching → acknowledged`。`acknowledged` 仅表示与本次原生命令、实例准确关联的成功调用回执已经持久化；`accepted` 是需要额外原生证据的业务接受事实，S2 不依赖它清稿，二者都不是 started/completed。明确接受前拒绝为 `rejected`，本地准备中取消为 `cancelled`；派发后尚未持久确认 ACK 且断链/超时/崩溃为 `unknown`。

- Host 必须等 prepared（含冻结内容）与 dispatching 分别落盘后才写 OMP。Main 收到有效调用 ACK 后，在同一事务保存 acknowledged 与对应草稿 revision 的消费标记，成功后才通知 Renderer 腾空仍对应本次提交的输入。事务不另改草稿正文或推进 revision；输入继续沿原保存序列工作。新编辑始终保留，通知丢失时由持久标记恢复有效草稿。
- 通信确认、业务接受和执行结果分别记录。当前固定 OMP v18.4.6 仍可先 success 后同 ID 异步 response error，再给出独立 prompt_result。首次 success 只证明调用确认；Host 不能在 ACK 或迟到 error 后提前释放已接受请求的关联。requestId 映射到 submissionId 与完整 target（processInstanceId/connectionGeneration/configContextId/nativeSessionRef），不按文本、generic idle 或 agent_end 猜结果归属。
- prompt_result(id) 的 completed/aborted/error、agentInvoked、sessionSettled 独立保存为有限结果观察；error 仅保存 retryable/httpStatus 等必要类型化摘要，不复制 provider 文本、诊断路径或正文。内置本地命令有时只返回 response.data.agentInvoked=false，该结果另标 native-local-response，不伪造 prompt_result 或 sessionSettled。agentInvoked=false 不证明没有配置/文件副作用。
- completed 只说明该输入的原生工作结果；sessionSettled=false 时仍保留后台活动约束，新鲜 get_state/control 与 session_settled 才能确认该实例闲置。prompt_result 不证明最终正文已到 Renderer，正文仍以 full 模式的 message_end 与阅读快照为准。
- 后续错误/执行中断与已持久确认的 ACK 分开：保留 acknowledged 事实及冻结原文，独立显示失败或执行结果未知，不倒写成从未发送、不因迟到 success 擦除错误。只有可靠证据证明接受前拒绝才标注该拒绝；一般异步错误不能推断失败阶段。没有逐提交身份的原生流只归属 Thread/会话。
- 准备/派发前持久化失败不发命令；ACK 与消费标记事务失败不清稿。结果可先于 ACK 保存，不能绕过对应 revision 的 ACK 消费条件。重复结果幂等，晚到 success/拒绝不清除已有失败或结果证据。
- Main 提交成功后按 evidenceId 确认 Host 的证据；提交失败显示覆盖缺口，同活 Host 至多保留 256 项未确认事实，按有界退避重送证据，绝不重写 prompt。未确认证据阻止正常 idle 回收/退出，即使 ACK 已保存且原生已闲置。重复 ACK 不占新缓存项；确认后至多保留 128 项、15 分钟的无正文身份以识别重复终态和迟到错误。缓存满、未决关联到期、无关联结果和 Host 再崩溃保留缺口，不承诺跨 Host 重放或零丢失。
- App schema 6 在现有 submission 收据 JSON 中增加有限观察，不存原生事件账本。升级按既有顺序恢复再生成 before-v6 备份和发布版本，失败不删库。重启把 dispatching 与已 ACK 但无结果的 unobserved 解释为 unknown；ACK 时间、已消费 revision 和冻结原文保留，持久终态保留。旧 schema 的 unobserved 不猜成功，旧 App 拒绝 schema 6，不开放旧原生会话写恢复。
- 当前 App schema 7 增加独立 `queue_change` 变更收据，保存待处理队列 destructive 操作的完整 target、trace、命令和原文；不覆写 submission，不作为自动消费队列或原生历史副本。派发前 dispatching 必须落盘，明确终态保留；失联或 ACK 持久化失败保持 unknown，不自动重发。begin/update/cancel 编辑暂缓控制不创建该持久变更记录。
- 启动顺序保持 `open → 至少 v3 + WAL → submission recovery → 后续 schema 迁移（至 v7）→ queue change recovery → publish`。submission recovery 必须先于升级备份；before-v6 保留 schema 5，before-v7 保留 schema 6 及已恢复的 submission。`queue_change` 仅在 v7 后可用，其恢复只把 dispatching 转 unknown，不发送原生命令；任一恢复或迁移失败不发布 AppStorage、不删库重建。
- ACK 丢失不能凭相同文本、队列长度或时间相近认定已确认；未知不自动重发。用户显式重新发送产生新 submissionId、关联原提交并提示可能重复；App ID 不创造 OMP exactly-once。重复点击/IPC 对同一 submissionId 只返回已知状态，不重复派发。重启 prepared 也不自动发送。
- 冻结原文以可查看、复制的持久发送记录保留；不能依赖原生历史已保存它。S2 不回收这份唯一可靠副本。后续只有原生持久化及引用可恢复性已确认后才可解除临时保留，unknown 不受普通缓存 GC 影响。收据不另造模型执行历史。

### 排队内容管理（2026-09-27 用户补充，D-11）

用户必须能看到真实待处理队列，并直接编辑、删除其中一项或调整顺序。OMP 仍拥有实际队列；App 提供投影和操作接入，不以本地展示变化冒充原生修改成功，不在前面另建自动消费的持久执行队列。

- 逐项身份、内容/顺序的修改能力和确认依据需核实固定版本。修改后的附件/引用重新准备与预检；保留原冻结提交及后续变更的关联，不覆写旧收据让历史看似从未修改。具体原生关联与落盘协议在接入证据明确后细化。
- 操作针对尚未消费的条目；原生已开始消费时不能宣称编辑、删除或重排成功。2026-09-27 用户确认：进入编辑即暂缓该条消费，保存后按新内容继续，取消则恢复原内容；当前执行不受影响，轮到编辑中条目时等待保存/取消，不擅自跳过执行后项。
- 暂缓必须有实际执行侧依据，不能用界面编辑锁冒充原生已暂缓；进入编辑与开始消费竞争时核实结果，已消费则明确提示不能按待处理项编辑。保存的新内容完成准备、预检并确认更新前不能释放暂缓；更新失败保留编辑内容并显示状态。
- 用户确认 macOS 红色按钮关闭窗口时：当前执行继续，未保存的队列编辑内容保留；轮到编辑中条目仍等待，不执行旧内容、不自动保存新内容，也不跳过后项；重开后由用户保存或取消。该规则针对关闭窗口，不等同 ⌘Q 退出应用或尚未定义的“关闭 Thread”。关窗、断链及恢复路径在接入时验证，Renderer 卸载不能自动提交编辑内容或释放实际暂缓。
- 编辑暂缓与用户点击停止产生的队列暂停是独立原因：保存/取消编辑只解除编辑暂缓，不能自动解除停止；点击继续也不跳过尚未结束的编辑暂缓。仅当相关阻止消费的原因都已明确解除，且执行侧确认状态后，才允许消费下一条。
- 修改/删除/重排后断链或确认丢失时标明结果未确认，保留用户编辑内容并重新核对；不盲目重试，也不静默把失败操作转为新的普通发送或干预。
- 对应功能接入前验证：列举/身份关联、三类操作、与消费并发、带附件编辑、失败/断链和重连一致性。现有实验未证明这些路径通过。若原生公开接口不足，先调查薄适配；需要改变所有权或长期 fork 时依据证据对齐，不静默削减已确认交互。

用户随后确认完整队列管理纳入 M2 首版验收；对应原生能力和暂缓消费机制必须验证。M1 保持内部闭环的基础排队/控制范围，不把完整队列管理变成所有切片共同前置。

## 3. 配置与首版认证（B3）

**首版新增/修复认证入口只交付两条：OpenAI 账户登录（OMP 的 openai-codex 路线）和 DeepSeek API key。** OpenAI API key 与 ChatGPT/Codex 账户登录不是一个认证入口，界面不能混称。这里收敛的是 GUI 初始化开发和验收范围；已有其他可用原生 provider/model 继续展示复用，不新增模型品牌拦截。其他 provider 的新增 GUI 认证后续逐项做，不能假设只是换名称：其他 OAuth、企业身份、本地服务等仍须各自验收。

- `configContextId` 标识解析后的配置根、profile、cwd 与非秘密的来源信息；真实环境值/凭据由宿主使用，不放进 UI 状态/日志。所有配置读取、认证及 OMP 执行使用同一上下文。
- 配置摘要与新认证命令携带明确的 `application` 或 `thread { threadId, workingDirectoryId }` scope 和同一 `traceId`。Main 在资源等待前从 Thread 仓储固定实际目录及原生环境，等待后复核关联；切换活动 Thread 不改写旧请求，删除或重关联返回 `stale-target`。application 使用 Main 拥有的固定隔离探测目录。Query key 与命令 scope 一致，回包身份不符不能进入成功缓存；认证续步与取消只按原 job 找固定来源。
- snapshot 全链只读，不以 `Settings.loadReadOnly` 代替凭据、模型缓存与文件迁移的验证。薄适配以有限只读 SQLite 事务读取已提交的数据库和 WAL；缺数据库不创建、legacy JSON 不迁移、不执行命令 key/helper、不联网、不加载项目 Agent/扩展。SQLite 的 WAL/SHM 协调文件允许由原生只读连接管理，不 checkpoint、不修改持久凭据/配置/模型缓存源。模型缓存通过 SQLite serialize 的一致快照交给私有临时库中的官方兼容校验、合并和 metadata 读取，退出清理。旧 schema、损坏或不安全路径、读取锁超时、远程认证、未观察账户目录和无法在有限读取内观察的外部配置引用均明确返回 `partial/unavailable` 与对应未知项，不把未知解释为无认证。2026-10-01 用户纠正共享配置回归后，取代此前将正常活动 WAL 当作不可读的工程限制；双向共享证据见 [M2 配置复用修复](../../.scratch/m2-first-release/configuration-sharing.md)。
- 推理选项从固定 SDK 的实际 metadata/helper 派生，区分 native default、explicit off 和支持的 effort（含 minimal）；不可调模型不给虚假菜单，requiresEffort 不提供 off。18.4.6 使用官方 `ThinkingLevel.Off` 显式关闭，`undefined`/`ThinkingLevel.Inherit` 表示未指定。空闲实例应用前复核能力，完成后显示 Host 的实际回读；未知操作结果不显示成功。
- 正常已配置路径零配置进入。Finder 启动缺少终端环境时，区分 absent / incomplete / incompatible / inaccessible；GUI 可选择原生配置根及必要环境来源，展示来源与作用域。不能误判成新用户后暗建默认配置，也不自动执行任意 shell startup 文件以“修复环境”。
- 不兼容格式禁止写入，不自动迁移外部 CLI；提供只读诊断、选择兼容上下文及明确修复说明。原生接口写设置，保存前重读、比较目标 revision/内容，保存后回读；App 内串行不冒充外部 CLI 互斥，record 冲突要求刷新重做，不能盲覆盖。
- 认证由原生实现管理 token、刷新及持久化；GUI 仅传秘密输入/显示挑战、取消与进度。OAuth 用系统浏览器，不依赖未来内置浏览器；回调/state/超时由原生路径处理，结束释放监听。API key 不进入命令行参数、日志或 App 偏好，走受控输入通道。新 key 验证/保存失败保留已有有效认证，不先删旧值。
- 原生设置 CLI 不等于完整认证 RPC。G1 确认随包产物能否暴露原生 auth；允许短生命周期的随包薄桥接（复用固定版本原生模块），不先建常驻服务、不自写 OAuth、不维护 Runtime fork。若需要长期 fork 或无安全可打包入口，阻塞认证切片，带证据对齐，不偷偷换登录方式。
- 验收分别覆盖：新用户完成两条入口、已有配置复用、取消/超时/无网络/无可用模型、认证刷新、App 重启、Finder 环境差异、旧配置不被误覆盖。列出模型不等于请求可用，不用真实计费请求当无提示的配置探针。

## 4. 内容包与附件（B4）

D-33 已确认最小 Tiptap：编辑器实例管文字、引用节点、选区与撤销等编辑状态，App 管版本化草稿与附件，提交适配生成 OMP 能接收的 payload。按需注册扩展并经 @tiptap/pm 接入必要的 ProseMirror 能力；不默认引入整套富文本 UI/协作服务，也不维护第二套直接 ProseMirror Composer。底层编辑机制可依赖 DOM，提交、权限、持久化和后台附件任务仍属于独立无头功能。

- 粘贴/拖入时将图片和附件复制到 App 私有内容存储并校验成功，之后不依赖外部路径仍存在。二进制按内容摘要去重；每个引用仍保留独立来源、文件名/MIME、字节数、捕获时间。不能因同内容而混淆用户多次附加。
- 2026-10-08 Composer 反馈补充：上述存储来源身份不变；同一 Composer 的重复附件采用可按文件名/MIME/字节数/已验证内容摘要去重，不新增重复输入，也不合并数据库来源。外部图片独立于正文/Undo，其他文件内联并参与 Undo/Redo；保存、不可变捕获与资源清理继续使用当前草稿真实依赖。详见 [input 合同](modules/input-context.md#可信结构化剪贴板t3-foundations-04)与 [Composer 规格](../../.scratch/composer-quality/spec.md)。
- 编辑器选区在附加时冻结文字、路径、行号及文件版本；从 Diff 附加时，同时保留所选侧的内容来源与捕获版本（如 Git 对象或工具记录），恢复和发送均使用这份冻结内容。文件、Diff 与输入模块共用该引用合同，同路径的不同版本不能混用。@ 文件在发送准备阶段读取冻结，显示“发送时读取”，文件消失/越权则阻止该次发送。排队后内容不随磁盘变化。所有转换记录输入摘要、转换版本、输出形式和覆盖缺口。
- 内容状态为 preparing / ready / failed，只有全部必需项 ready 才提交。内容包不可变；修改草稿产生新版本。准备阶段超限/失败可移除或重试，不自动截断、改模型、只发送文件名。
- 2026-10-07 D-10补充：跨Thread复制动态@文件/目录时，Main在复制请求的有界export准备阶段按源Thread实际授权捕获内容与版本，目标使用私有冻结快照及新ID。原草稿仍发送时读取；目标路径与版本只是溯源，不授予回读原项目/目标同名路径的权限。目录仅冻结完整直接条目清单；失败/超限/过期明确可读降级。选中依赖、snapshot/import/history/持久采用和实际ACK清理合同见[T3规格](../../.scratch/t3-foundations/spec.md#用户选项1复制冻结来源与版本)。
- 文本文件明确编码；二进制走支持的原生资源/图片能力，不能假装都是文本。PDF 优先原生可靠通路，否则本地解析文字并按需渲染页面；扫描/图表不能仅抽空文本即宣告成功。向用户展示转换结果和损失，模型不支持需要的图像时阻止发送该表示并给出换模型/显式仅文本选项。默认不用第三方文档解析服务。G1 验证解析/渲染与模型适配，无法完整覆盖时不判 V1-04 通过。
- 模态检查须覆盖实际 provider/transport 与兼容设置，不能只看模型声明的 `input`。v18.3.0 的 `compat.stripImageInput` 可在部分传输路径移除图片，即使模型声明支持图片；G1 用可控样本核实实际发出的内容。不把静默丢图当作成功，按上条阻止不支持的表示或由用户显式选择降级。
- 首轮预算：单源文件 25 MiB、单提交原始内容 100 MiB、PDF 100 页，实际模型限制更严则从严；预检后报具体限制，可记录原因调整，不隐藏处理大文件。内容存储软上限 1 GiB，达到上限只清无人引用的派生缓存；活跃草稿/准备提交/unknown 收据固定保留，容量仍不足时明确拒绝新增而非删用户输入。
- 原始内容预算不等于 RPC 输入容量。v18.3.0 文档的 v2 分片针对 stdout，输入仍是单个未分片 JSONL 对象；按目标版本声明及实际能力验证编码后字节数（含 base64/JSON 开销），不能假设可把附件拆成多条命令输入。G1 核实可复用的原生资源通路、显式转换或限制及失败行为；未验证前不承诺预算内任意附件均可发送，不能静默丢内容。
- 原件、派生项有引用计数与一致性扫描；最后引用释放后延迟 7 天清理，可手动清理无人引用缓存。原生历史未自持久附件时保留 App 引用依赖；不能假设 accepted 即可删原件。损坏/丢失显式标出并允许重新附加。私有文件限制本机权限，日志无正文/秘密；这些业务内容不是诊断日志。

## 5. 最小权限与信任（B5）

将项目执行信任与 App 文件访问范围分开设置，不呈现为 Agent 权限逐级增加的三个档位，也不建设规则编辑器：

| 设置 | 选项及实际含义 |
| --- | --- |
| 项目执行 | 新目录默认“仅浏览”：文件树、只读代码和 Git 差异，不启动项目 Agent、shell、项目扩展或语言服务进程；只读服务不得加载项目代码。显式“允许项目执行”后才允许启动任务与加载原生项目配置/扩展；Agent 使用当前 OS 用户可访问的资源，不承诺目录沙箱。 |
| App 文件访问范围 | 默认项目根及显式授权的文件/文件夹；额外授权首版只授读取，可查看和撤销。高级选项“App 文件完全访问”放宽 App 宿主文件接口的根限制，仍受 OS 用户权限；不授予项目执行信任、不获得管理员权限、不绕过 OMP 原生审批。 |

两项设置分别保存在规范化目录维度，不因开启 App 文件完全访问就启动 Agent，也不通过父目录信任或当前项目设置自动授权所有项目。额外读取授权来自用户文件选择/拖入。撤销阻止对应的新操作，撤销项目执行信任时，运行任务需停止后才可声称已降级；不能承诺撤销收回已交给 OMP 的数据。

Renderer Node 关闭、contextIsolation 和 sandbox 开启，受限 preload、IPC schema/source/Thread/资源归属校验。Main/宿主规范化路径、解析 symlink 并校验实际目标，模型输出路径不构成授权；文件句柄打开时复核，不能仅作字符串前缀判断。App 的“只读 Git”调用禁止会执行用户项目脚本的外部 diff/textconv 等选项。

沿用历史安全基线：模型输出、HTML、链接和附件均为不可信内容。展示或读取它们不授予脚本执行、文件访问或宿主调用权限；Markdown/HTML 渲染、链接打开与后续内嵌网页各自保持内容边界，外部内容不能获得应用特权 preload。相关切片验证危险 URL、活动内容与越权资源请求，不因某渲染库可用就视为边界已验收。

OMP shell/工具原生权限和 App 文件接口是两个执行面。项目信任说明须明确 Agent 可能访问当前 OS 用户可访问的其他资源；未验证原生隔离前不得出现“Agent 仅能改当前目录”的承诺。如果后续要求真正工具沙箱，另行评估。Side Chat 真只读必须在工具注册/能力层限制；无法证明就不接可写工具，不能只放一段只读 prompt。

D-40 用户终端同样受目录级项目执行信任准入，使用当前 OS 用户权限；App 文件完全访问不授予 shell 启动权限。撤销时需处理该目录的存活终端再声明降级，不把任意 shell 命令包装成 App 文件沙箱。具体许可/fence与工作目录规则单源见[终端契约 §2](terminal.md#2-目录信任与-shell-环境)。

## 6. 有界事件与恢复（B6）

本节面向 OMP 执行/阅读投影与原生历史；其中“始终消费原生 stdout、不使 OMP 因 App 缓存卡死”不能套用为用户终端永不 pause 的规则。D-40 用户 PTY 的屏幕快照、消费确认、pause/resume与预算由[终端契约 §4–5](terminal.md#5-输出确认背压与预算)维护，输出不存成 OMP 历史或本节补充事件存储。

| 数据类别 | 策略 |
| --- | --- |
| 流式文字、瞬时进度 | 同一 block 内合并；工具/交互/终态前刷新，完整正文可分页，不保留每个 token 事件 |
| 消息/工具/交互/终态 | 保序投影，不能仅留下最后一条状态；可从原生持久化重读的记录用原生引用 |
| 无原生重读保证的工具/子 Agent 输出 | 只保存恢复 UI 必需的内容与原生关联，App 有界补充存储；不据此重建 Agent 上下文 |
| 诊断 | 独立有界队列/轮转，与业务输出存储分离；详见 diagnostics |

工具证据与引用读取带原生关联、内容和来源的记录，不依赖显示卡片。卡片分组、摘要或裁剪不改变这些内容；恢复仍复用原生历史与必要的有界补充。对可恢复的已完成记录，实时显示与重开后的最终内容、来源及记录关联应一致。

Renderer 按当前需要订阅：后台 Thread 保留状态、待答、错误与结果提示，正文详情按阅读需要同步。Host 始终消费原生输出，切回详情按快照与增量恢复。具体订阅接口在阅读切片确定；按范围过滤时，序号与水位须采用同一范围，避免把有意省略误判成丢包。

Host 按 connectionGeneration + 单调 seq 产生投影；快照包含 watermark，先订阅并缓冲增量，再应用快照并接 > watermark 事件。缺号触发重同步，旧代次丢弃。历史分页独立于实时尾部；后台无窗口仍读取。持久化缺口、原生记录未落盘、超限截断均有用户可见占位与范围，不显示虚假完整。

上述历史分页是产品合同，不代表 get_messages_page 已满足运行中读取：v18.3.0 在 streaming/compacting 时返回 session_busy，且读取 session.messages。G1 须分清持久历史、当前执行上下文和实时显示尾部，验证不启动 Agent 的历史浏览、执行中重开窗口并补页、压缩/分支变化后的来源和位置一致性。只读原生记录或其他原生读取入口是待验证路径；不能以一次全量读取冒充有界分页，也不能靠扩大内存掩盖缺口。

初始每活跃会话内存尾部预算 8 MiB，事件补充存储每 Thread 100 MiB、全 App 1 GiB；超限先回收已可原生重读的缓存，再转分页。无可回收空间时记录缺口、警示恢复覆盖不足；不阻塞读 stdout 导致子进程卡死，不删用户待答交互/未决提交。预算不约束 OMP 自己的磁盘记录，界面不得把 App 缓存清理叫删除原生会话。

## 7. 诊断与性能验收预算（B6）

沿用 D-21/D-22；Main 负责日志设施，业务走实际 Renderer→Host 或 Main 路径。跨边界共享 traceId，错误类型、观察点/报告源/归因/恢复责任分开。日志失败不阻断正常任务，但必须有独立的退化指示与 dropped 计数。

初始实现预算：每进程日志待发队列 1 MiB / 1000 条（先到者）；批量最多 100 条/100 ms，关闭时有界 drain 2 s。单日志文件 10 MiB、轮转总量 100 MiB、最多保留 7 天。关键错误优先于 debug，但不承诺异常风暴零丢失；debug 限时 15 分钟，默认不记 token 级事件、正文或秘密。磁盘满/写失败不得递归记日志形成风暴。

专项测量用于相关高风险改动、实际性能退化与 M1/M2 组合验收，不要求每个切片或普通修复重复。需做诊断性能专项时，固定机器与版本、相同输入/输出重放，比较日志开关各 5 次的中位数及尾延迟：默认诊断使 p95 输入反馈增加 ≤5 ms，任务完成时间增加 ≤3%，稳定内存增加 ≤20 MiB；输入反馈绝对 p95 ≤50 ms。以上是待测验收目标，不是已实现数字。控制其他变量、记录样本数量和方差；有波动不能挑最好一次宣称通过。

M2 性能组合验收的负载至少覆盖（M1 仅当前已交付能力的代表性负载，不把全部场景搬到每张票）：3 个并行 Thread、累计 10000 条消息、单工具 10 MiB 输出、后台持续 30 分钟、20000 字 Composer 编辑及中文 IME、多附件准备、窗口重开、日志磁盘满和慢写。队列/缓存不越预算，停止产出后内存趋稳；长会话原生/业务数据仍可增长，需分别报告，不能把全部 RSS 归给日志。真实模型网络延迟不用于归因本地开销；确定性样本测量与真实 OMP GUI 路径验收都需要。

## 8. 开发入口、里程碑与门槛（B7）

设计层已可进入分阶段开发，实际授权与进度以近期 spec 为准。2026-09-27 用户要求减少前期验证，规则单源见[无头功能合同](headless-features.md)，本节不复述。与契约相关的边界是：后续功能的细节不阻塞基础工作；会改变用户承诺或要求 Runtime fork 的发现才重新对齐。

| 阶段 | 交付与出门条件 |
| --- | --- |
| G1 关键风险核对 | 官方文档/固定版本源码/既有证据优先；仅尚未回答且影响关键承诺的未知才需前置实验。涉及实测时隔离临时配置，按风险核对命令接受证据与后续失败、执行中历史读取、停止与队列的实际结果；另按切片验证认证薄桥接、原生会话占用/恢复、项目加载时点、附件/PDF 的编码后输入边界与实际模态、Composer IME/Monaco worker。逐项记录能力、缺口与可行替代；不要求先做所有 UI，不接个人凭据作自动实验 |
| M1 内部可运行 | 已有可用原生配置、一个前台任务完整闭环、文字/选区、交互/停止/排队、只读文件与 D-20 Diff、提交恢复、各层诊断和故障路径。基础身份支持多 Thread，但不要求此时多任务 UI 全验收 |
| M2 首版完整验收 | foundation V1-00–10：两种新用户认证、多 Thread 并行、子 Agent 合理默认配置与当前 Thread 后续模型/档位覆盖、完整队列管理、全部指定输入、长输出/恢复、macOS 本地包；仅已验证组合标支持。逐项真实 GUI 证据，含性能与故障测试；局部失败不能用 M1 通过代替 |
| M3 后续渐进 | 子 Agent 自动降档/调整确认/倒计时等高级策略、历史操作精细 UI、Monaco 编辑/语言服务、Side Chat、浏览器、终端、PNG 分享、Git 写操作/worktree 管理，按依赖逐项规划，不固定全部同时交付 |

G1 的阻塞仅限尚未解决的关键风险，不是每个能力必须独立实验的门槛；常规接入可实现时检查。具体而言：认证受阻不阻塞 M1 的已有配置闭环，但阻止 M2 认证通过；IME 失败阻止对应输入切片的接入验收，不将 D-33 已确认选型降回待定；不能保证会话单写则限制恢复入口；权限未可执行就不显示虚假受限模式。性能验证随 M1/M2 真负载开展，不要求在零代码阶段“证明无感”。

## 2026-10-08 同原生会话冷续作（D-24修订）

用户明确要求冷重启继续原会话，取代旧一律只读的交付边界。已有私有绑定经过目录授权/规范路径/header ID与cwd检查、生命周期lease与旧进程身份清理后，由SessionManager.open打开原文件；不fork、不使用“最近记录”，不新建替代会话。ready必须同sessionFile/sessionId，恢复原生已保存上下文到阅读镜像后再允许新提交。未知旧提交仍unknown，恢复启动不能补发prompt或反推原结果，SDK异常尾修复不结算App收据。

lease覆盖支持的所有d-pi启动/控制入口并持有到原生进程组确认关闭；异常死亡由OS释放，持久身份用于核实旧Main/native后清理，不以旧PID单独杀进程。不接管外CLI目录。任意同UID外程序绕过协议直接打开d-pi私有文件不在互斥保障内，不能宣称官方CLI已具有执行锁；真正占用/身份未知/损坏/授权撤销时停止恢复并保留可读内容，提供具体原因与重新检查入口。

2026-10-08 后续 CLI 续接修订：用户要求已结束 CLI 的历史在 GUI 原地继续提问，取代“不接管外 CLI 目录”和来源一律只读限制。配置根、canonical 文件、header ID/cwd 与目录 grant 核对后使用原文件/ID；原文件所在目录的文件粒度 d-pi lease 覆盖所有支持的 App 启动与执行全周期。接入前以真实打开写 FD 和该项目存活的 OMP CLI 检查既有外部占用（idle CLI 无 FD 时也阻止）；不抢占/终止外 CLI。没有修改外 CLI，启动快照不等于共享执行锁；在 GUI 执行中另起未合作 CLI 打开同文件，仍属于绕过协议的外进程，不在互斥保障内。此限制不再导致已退出 CLI 的历史永久只读；失败保留原 Thread、历史与新输入，可原地重新检查。

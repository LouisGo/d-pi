## 用户场景与所有权

用户选中主会话内容发起独立问答，携带发起时上下文，可追问、只读看代码、独立选择模型/思考档位；历史关联主 Thread 和原文位置。同步主会话最新进展、把结论发回主会话都是显式操作。

旁路问答拥有独立身份、历史关联和执行生命周期；关闭面板释放视图但保留历史。它不复用主会话的可写执行状态，不把问题自动排入主会话。原生独立会话绑定及资源回收在本切片确定，持续后台执行仍受统一宿主退出规则约束。

## 与现有模块怎样组合

| 依赖 | 取什么 / 做什么 | 对外结果 |
| --- | --- | --- |
| [阅读](conversation.md) | 捕获选中文本、原文位置和当时可用主会话上下文，注明缺口 | 可解释来源的旁路初始输入 |
| [输入](input-context.md)、[配置](configuration.md) | 独立草稿、引用和模型能力 | 冻结旁路提交；切换生效时点需明确 |
| [执行](execution.md)、[宿主](runtime-host.md) | 复用提交/接受/停止机制，但采用独立会话及受限工具能力 | 独立问答和交互，不修改主会话状态 |
| [文件](files-editor.md)、[Thread](threads.md) | 明确的项目关联、执行准入及只读代码能力 | 可追问的代码上下文，权限失败可见 |
| [存储](app-storage.md) | 关联、草稿与必要记录；原生历史仍由原生保存 | 重开后能找到旁路与来源 |

“发送到主会话”进入主会话输入/提交合同，由用户明确提交；不能绕过草稿版本、队列和 unknown 规则。显式同步导入新的上下文快照，不能随主会话流式变化偷偷改写已发送内容。

## 开始开发前需要解决

先证明工具注册/能力层真正只读：不提供可写工具、任意 shell 或可绕过限制的项目扩展。只读 prompt 不构成限制；项目仅浏览默认也不因此自动授权启动 Agent。不能落实就不接可写能力，并报告对代码问答的具体影响。

然后确定上下文容量/缺口表达、独立原生会话恢复、模型/档位切换的生效时点和并行关系。复用[原生多会话与宿主工具证据](../../validation/runtime-feasibility.md)只能证明部分机制，不代表 Side Chat 只读已通过。

## 验收场景

主会话运行时发起旁路，不影响主队列；旁路写文件/执行任意命令被实际能力拒绝；源消息变化仍保留原引用；显式同步后来源清楚；关闭重开历史仍关联；回送内容需走主提交；上下文不足不假装包含完整历史。按本切片完成无头验证后接正式面板，不提前建设通用多 Agent 编排层。

# 设计 Token、组件边界与密度

日期：2026-09-27。状态：用户要求及工程合同；S1基础接入已有验收记录，后续组件按实际改动检查，具体覆盖见S1交接。补充 D-17/D-32，与[图标合同](icon-system.md)、[无头功能合同](headless-features.md)共同约束 GUI。适用于样式、组件、页面和外部 UI 源码接入；不将视觉 token 放入 OMP 协议或无头业务数据。

2026-10-06 最新要求：基础、配套和业务组件保持同一视觉体系；light/dark 均为必备主题，颜色角色由同一变量体系联动。取消 normal/compact 切换，以原 compact 尺寸作为唯一默认布局，不再区分两种产品密度；取代此前双密度建设与往返验收要求，历史证据保留。自有组件封装要求继续有效。

## 目标与当前缺口

用户最终澄清的核心目标是共享样式值只有一份权威定义，而非要求所有样式代码集中在一个文件。以 primary 为例：基础主题源定义 `--primary`，Tailwind 的主题映射引用该变量，CSS Modules 与普通 CSS 同样引用它或同源别名；不能在 Tailwind 配置、模块样式、全局样式或 JS 中分别维护等值副本。主题作用域可以在集中主题源中定义不同模式的值，不构成消费者各自定义。深浅主题、状态及前景色的映射仍集中管理，不等于所有颜色都依赖 primary。

组件局部布局和选择器可以就近维护；颜色、间距等共享设计事实及其派生关系集中维护。需要 JS API 的适配层读取/订阅同一来源，不能手工抄一份常量。自动生成的映射若确有必要，必须有唯一输入且禁止手工双写，不为此预建生成平台。

用户要求初期建立统一 CSS token 与管理规则：修改主题色、辅助文字色、间距等通过集中来源传播，既有页面不逐个补丁。2026-10-06 取消密度切换，原 compact 尺寸成为唯一默认基线；AI 不得为了一个功能任意增加局部色板、尺寸体系或破坏组件 API。此前仅有“自有设计变量”和可选 lint 的方向，不足以保证此目标。

S1 首个正式 GUI 前建立最小 token 合同、组件约束及 `@shadcn/lint` + Oxlint 检查，与 S1 一起验收；不等待完整组件库，也不提前建设所有远期组件。S1当前实现与证据见[S1交接](../../.scratch/m1-s1-project-draft/handoff.md)。

## 开源依据与样式表达选择

用户进一步要求以成熟开源实现为依据，不自创体系；同时明确允许 CSS Modules 和全局 CSS。采用依据见[固定源码研究](design-system-references.md)：shadcn 官方 Base UI 组件/主题为主，Base UI 官方 CSS Modules 为复杂交互参考，同栈应用仅作组织对照。优先延用 shadcn 语义名称、size/variant 和 Tailwind 原生机制；下文的分层表示职责，不要求自建 token 编译器或多层别名框架。

选择方式是工程判断策略，不是“场景 → 固定技术”的分派表，也没有必须先尝试 Tailwind、失败后才准用 CSS 的顺序。先看现有实现及适用的上游模式，再综合比较可读性、复用边界、级联影响、动态数据需要和后续修改成本，选择 Tailwind、CSS Modules、全局 CSS 或它们的合理组合。

例如，伪元素用少量 Tailwind 类即可清楚表达时无需迁到 CSS Modules；已经由局部样式清楚管理的布局也无需改成工具类。这些例子只说明判断方法，不形成新的默认路由。

无论选哪种方式，都共享 token、主题/密度和组件契约，明确样式归属与影响范围。全局规则控制污染，局部规则不能越权重绘别的组件；动态几何可由适配层提供运行时值。注意级联层、导入顺序和 portal，cn/tailwind-merge 不能消除普通 CSS 级联冲突。正常选择不需要单独审批，不以 Tailwind 使用率衡量质量。

## 一处定义，分层消费

| 层级 | 内容与所有者 | 使用规则 |
| --- | --- | --- |
| 基础值 | GUI 设计系统集中定义色值、间距基准、字阶、圆角等 | 字面色值与设计尺寸在此定义；业务页面不另造基础值 |
| 语义 token | surface/foreground、primary 与对应文字、border/focus、状态色、布局间距、控件尺寸等角色 | 主题和密度映射集中维护；颜色角色不按页面或当前色值命名 |
| 组件契约 | 共享组件定义 size/variant、状态和必要的私有别名 | 消费语义 token；私有别名必须有用途且派生于统一体系，不能藏一套独立数字 |
| 页面组合 | 选择组件、变体与布局角色 | 只控制合同允许的布局属性，不重写组件颜色、内部 padding、圆角或字号 |

CSS 自定义属性作为共享视觉值的单一来源，通过 Tailwind 主题映射提供可读的语义工具类。适配 shadcn 使用的变量名称到这份来源，不维护第二份平行色板。唯一入口是 `src/app/renderer/styles/tokens.css`（`@theme`/CSS 变量），供 lint 与文档引用；存量 `:root[data-density="compact"]` 覆盖随首个布局切片收敛到默认值，本合同不复制数值。

普通布局可直接使用统一 Tailwind spacing 标尺，不要求每个 p-4/gap-3 再起语义名。需要跨组件保持一致的控件、行和面板尺寸角色集中映射；仅禁止任意值不能证明视觉体系成立。禁止脱离标尺的随意视觉值，不禁止结构几何、原生 CSS 变量引用或清楚的计算表达式。

主题色是语义角色及状态/前景色的一组映射。更换一个角色的基础输入，应通过已有映射覆盖其使用位置；文字对比度、hover/disabled/focus 和深浅主题仍须验证，不能假定任意新色值都可读。

## 同一视觉体系与颜色联动（2026-10-06）

基础控件延伸到配套组件和业务组合时保持一致的视觉语法。Codex 截图用于判断整体连贯性；不能将多个参考库的原样风格拼接起来，也不能将“全部用了变量”当作视觉已经统一。

图标动作的主图标独立居中；未读数、状态点和辅助读屏文案不能作为额外的正常流内容挤占位置。自有 IconButton 的 indicator 插槽负责脱离文档流、锚定角落和排除命中；包括空状态、数值0、长标签与禁用状态。带标题的项目/会话行仍保留正文信息流与不收缩的图标。几何验收比较实际SVG与按钮中心，不能只检查align-items声明。

| 角色 | 体系规则 | 组件组合中的约束 |
| --- | --- | --- |
| 圆角 | 控件消费 `--radius-control`，容器消费现有 `--radius`；需要浮层、胶囊等区别时建立有限的语义角色与派生关系 | 同类 Button 不因所在页面从 4px 变为 16px。不同角色可有合理差异，但同角色全应用一致，不按页面另起值 |
| 间距与尺寸 | 默认紧凑布局的控件高度、内边距、行距和间距标尺集中定义 | Toolbar、菜单、表单和 Composer 使用同一控件规则；业务组合只安排允许的外部布局 |
| 文字与图标 | 标题、正文、辅助文字、阅读正文分别使用已有文字角色，图标经自有 Icon Layer | 不在业务视图临时改字阶、字重、图标尺寸；长文可使用阅读角色，不将全部文字缩成控件字号 |
| 表面、边界与层次 | 工作区/控件/浮层按语义 surface、border、overlay 和明确的阴影角色组织 | 不给每一层都加卡片、阴影或不同描边；同类浮层保持一致的圆角、边界和层次 |
| 交互状态 | default、hover、active、selected、disabled、focus-visible 由共享组件/variant 映射 | 同一动作在基础、配套和业务区域使用同一反馈；不能只对单个业务按钮补局部颜色 |

light/dark 两套主题都必须覆盖所有自有界面，包括 Portal、空态、错误态、选中/禁用/焦点状态和专用内容适配。颜色角色沿用 background/surface/foreground、primary/primary-foreground、muted/muted-foreground、border、accent、destructive 等现有命名；辅助/副标题文字优先使用 muted-foreground 等真实语义，有缺口时在唯一来源扩充，不按页面定义 subtitle 色板。

颜色联动是集中主题输入与派生映射的结果：每套主题集中维护基础色与角色关系，相关 hover/active、选中底面和前景色通过同源引用或适当的派生计算得到；需要独立调节的辅助文字角色也在同一来源定义。更换主题配方或某个角色只修改集中来源，不逐组件补色值。联动不表示所有颜色等于 primary，也不能仅改主色而留下旧的主操作状态色。派生方式结合对比度确定，不预建 token 编译器或主题编辑平台。

当前 token 文件含单独定义的主操作状态色，尚不能据此宣称任意主色已能完整派生。首个布局切片应收敛实际经过的颜色关系与共享角色；用代表性主操作、导航选中和辅助文字验证传播、light/dark 对比度与组件一致性。

## 默认紧凑布局，取消密度切换（2026-10-06）

用户最终明确取消 normal/compact 切换，以原 compact 的尺寸作为 normal，即默认布局；产品不再区分两种密度。当前只有一套默认紧凑布局，不提供密度选项，不预建第二套尺寸或将密度往返测试作为交付前置。light/dark 两套颜色主题仍必须完成。

- 集中定义一套默认紧凑的控件、行和布局角色；原 compact 值收敛到默认 token，页面不新增 `if (compact)` 分支、normal/full/compact 密度变体或独立覆盖样式。紧凑不等于整体 zoom/transform 缩小，保留可点击区域、阅读字阶和焦点可见性。
- 当前生产代码仍有 normal 默认、compact 覆盖和密度切换，尚未完成本条要求。首个布局切片需让新建/缺省以及旧偏好恢复的 UI 都使用唯一默认紧凑尺寸，收敛 token 为一套实际样式并撤下密度切换入口、命令及样式分支。
- 旧持久数据中的 normal/compact 字段只作读取兼容，不再决定实际尺寸；在 preferences 边界处理旧字段，应用公开的外观设置不再提供可切换的 density。无需为此删除数据库或 DROP 旧列，也不继续写入一种新的产品密度选择；必要兼容写入是存储实现细节。保留旧备份/恢复及历史迁移，不用重建用户数据解决兼容。
- Portal 继承同一 light/dark 与默认尺寸来源；Monaco、后续终端等由所属适配层消费同源主题/尺寸，不另建色值或尺寸副本。真实字体、容器几何及测量值变化才使缓存失效，不为已撤下的密度切换保留新路径。
- 图片、语法色、Diff 和品牌图标保留其语义映射，不全部染成主色或随控件尺寸等比缩放。未来如重新开放密度，另按用户决定扩充同一体系，本次不预建第二套。

重新排列区域和响应式隐藏仍由布局约束负责，不声称改一个 CSS 变量能自动生成任意布局。

## 组件体系与变更纪律

Base UI 负责基础交互，shadcn 源码接入后统一使用本项目 token、Icon Layer 与组件 API。引用外部源码不豁免颜色/尺寸规则。

### 自有组件库与实现选择（2026-10-06）

用户明确要求：采用外部 UI 能力时至少经过一层 d-pi 自有封装，应用中的组件消费者只使用 d-pi 组件库的公开 API。Beautiful UI、Tool UI 是组件写法、组合与交互表达的重要参考，不是直接引入整套库的决定。这是 D-32/B-02 自有 API 基线的进一步明确；基础交互仍以 Base UI 与 shadcn 官方 Base UI 源码为主。

自有封装可以很薄，也可以由多个有明确职责的层组成。它必须实际管理项目的样式、变体、交互约定和公开能力；仅改名转导出上游组件、公开整个上游 namespace，或将复制的源码目录直接当应用 API，都不满足此要求。兼容的部件组合方式和标准 DOM 属性可以保留，不必为了封装重写成熟的焦点、键盘或定位机制。

```text
页面 / 功能视图 / 工作台组合
              ↓ 仅使用 d-pi 公开组件 API
d-pi 基础组件 / 配套组件 / 业务组合（按需）
              ↓ 内部实现与适配
Base UI / 选择性改造的上游源码 / 专用渲染与编辑能力
```

这些类别表示可组合职责，不要求每次调用穿过三层。允许业务组合直接使用基础组件；所有借用的 UI 实现都在自有边界内。

| 类型 | 拥有的职责 | 推荐写法与依据 |
| --- | --- | --- |
| 基础组件 | Button、Field、Menu、Popover、Dialog、Tooltip、选择控件等的交互与视觉契约 | 自有薄封装 Base UI，按需改造 shadcn 官方 Base UI 源码；Beautiful UI 的视觉不能代替这些控件的交互基础 |
| 配套组件 | ActionGroup、StatusRow、ToolResultFrame、AttachmentPreview、ContextChip、空态/反馈等可复用呈现 | 使用自有基础组件组合；参考 Beautiful UI 的部件/状态表达与 Tool UI 的数据/动作分工，合适时选择性改造源码 |
| 业务组合 | Composer、AgentInteraction、Queue、Subagent、文件工作页等 | 在所属功能内消费真实投影与操作合同，组合自有基础/配套组件；业务协调器不放进通用组件库 |
| 专用适配 | Tiptap、Monaco、Streamdown、面板原语及未来终端/浏览器的接入 | 库导入与资源配置留在对应适配内部，对消费者提供 d-pi 接口；保留原有事实与资源所有权 |

选实现时先查现有组件，再比较三种方式：已有 d-pi 组件组合足够时直接组合；成熟底层交互适用时薄封装；上游配套组件与需求贴近、改造成本合理时取源码。若只需其信息结构，或源码夹带演示状态、全局样式及较多无关依赖，则参考模式自行组合。源码复用不是默认目标，不为保留上游代码扩大项目依赖。

封装层的验收内容：

- 公开 props、事件、状态、部件、ref/焦点和可覆盖范围由 d-pi 维护。消费者无需 import 上游组件、类型或上下文才能使用；可在内部复用适用类型，但不能让应用依赖其私有 API 或任意透传配置。
- 配套组件通过显式数据与意图回调工作，不自行调用 IPC、创建 AppModel、重试提交或推断执行成功。回调完成、局部 loading 和按钮禁用不等于 OMP 接受/执行回执；过期、unknown、失败由所属事实投影表达。
- 样式、Icon Layer、文案、主题/密度、Portal、键盘与 reduced-motion 接入项目约定。共享基础控件的内部外观通过其 variant 扩展，不从配套组件用 important 改 padding/圆角等绕过合同。
- 复制源码记录仓库、固定 commit、实际文件、许可证、传递依赖、适配理由与本地修改；保留必要声明。上游更新经过比较与验证，不自动覆盖本地 API、样式和行为。

“自有组件库”是项目拥有的公开组件层，不要求立刻发 npm 包、建 monorepo 或将所有业务组件集中到一个 barrel。基础与配套组件提供按能力的明确入口，业务组合继续按功能归属组织并通过自有公开入口使用；不以统一库名制造反向依赖。

当前 `src/app/renderer/components/ui/button.tsx` 已有 Base UI 封装，但仍直接组合上游 Props，不能据此宣称完整公开能力已收敛。基础目录目前是 app 私有；configuration 等模块不能反向导入它。其现有原生按钮共享 CSS 是存量过渡方式，不代表已满足最终自有组件入口要求。后续相关切片先确定跨模块可依赖的 renderer UI 公共归属，再迁移消费者；不复制第二套 Button 或绕过 `architecture/modules.json`。

后续接入须检查消费者导入边界，以及组件的主题/密度、焦点/键盘、状态和资源保留。直接依赖外部 UI 的允许位置限于自有实现/适配内部，边界检查按实际落点接入现有门禁。本轮只确认写法和文档要求，尚未新增导入规则、迁移存量组件或安装依赖。来源比较见[固定源码依据](design-system-references.md#ai-组件的写法与配套组织2026-10-06)。

组件提供经过设计的 size/variant；调用者的 className 只允许该组件合同规定的布局属性。需要新的表现时先检查已有 token/variant，确有语义缺口再在共享层扩充并更新受影响使用处与验收样本。不为单个页面覆盖全局变量、堆叠高优先级选择器或复制组件绕过约束。第三方无法通过公开 API 调整时，可在所属适配层窄范围使用必要的 important，并说明原因与影响，不把它当默认覆盖方式。

体系可以演进，但变更必须解释影响范围；新增 token 要有语义、来源、主题/密度行为和使用处，避免每个像素一个 token。重大视觉方向、默认行为或范围变化按 AGENTS.md 先与用户对齐；常规复用与局部工程实现自行处理。不能通过关规则或放宽组件合同迁就一次违规实现。

## 指针、点击反馈与文本选择（2026-10-06）

用户已确认的全应用规则：点击目标禁止手形 `cursor: pointer`，统一为 `default`；输入/内容选择的 `text`、编辑器分隔条的 resize 等功能性指针保留。基础样式单源为 `src/app/renderer/styles/interaction.css`，由应用样式入口加载，覆盖 body 级 portal。

- 组件默认外观须能识别操作入口，hover/active/selected/disabled/focus-visible 分别表达含义。共享 Button 管理主操作、ghost、navigation 与 icon；主操作按下色来自 `--primary-active`，其他状态复用现有主题 token。折叠标题沿用原生 disclosure，文字链接默认有颜色及下划线。
- 鼠标 hover/active 使用背景与文字反馈，不因选中状态新增彩色 border、outline 或 ring shadow。键盘 `:focus-visible` 保留统一主题焦点轮廓；普通鼠标按钮焦点 `:focus:not(:focus-visible)` 不显示轮廓。输入框的原生 focus-visible 判定、编辑器 caret 和浮层焦点协议继续保留，不能全局禁用焦点提示。
- 默认 `user-select: none`。需要阅读/复制的正文、工具输出、历史、收据、原生交互及队列文本由内容拥有者加 `data-selectable`；输入/textarea/contenteditable 按原生语义开放。trace、Thread 身份、目录路径、file-meta 内容、运行来源、附件预览和 alert 是中央规则登记的内容例外，不按所有 p/span 或整个工作区开放。
- 可选择区域内的按钮、链接、summary、导航/选项及其控件标签仍不可选；消息 heading 与装饰图标也不参与正文选择。新内容区域优先使用 `data-selectable`，不另写 select-text/all/auto、内联 userSelect 或局部 user-select 例外。
- configuration 模块不能反向导入 app 私有 Button。其原生按钮使用静态 `ui-button` 加 `ui-button-primary/ghost/navigation` 接入同一份共享样式，保留原有表单/disabled 行为；不另建颜色或交互状态。其他 app 视图使用共享 React Button。
- Monaco 0.57 的 unlayered CSS 与动态 inline cursor 由中央适配规则限定到 editor/hover/menu 作用域覆盖。普通点击目标和编辑器使用窄范围 important；编辑区 text、sash resize 明确恢复。不对整个应用使用 `* { cursor: default !important }`，不覆盖 Monaco 自有选区机制。

源码门禁 `pnpm lint:interaction` 检查 CSS、工具类、静态内联/命令式赋值和原生按钮的共享样式接入；在 `check:fast` 与 `lint:design`（因此完整 `check`）中执行。CSS 文本选择例外只允许中央规则定义，违规失败。扫描只证明可静态识别的自有代码，不冒称能解释任意动态 JS 或第三方 DOM。

修改中央规则、相关控件、内容标记或升级 UI 依赖时运行 `pnpm validate:interaction`：隔离 Electron 使用正式 App/组件及真实 Monaco/Diff，验证 computed cursor、默认不可选与鼠标拖选例外、Monaco 键盘选区、控件/portal 覆盖、hover/active/disabled/focus-visible 和主题/密度。测试桥接使用 fixture，不认证、不执行 OMP，也不代表真实供应商或用户认可。实现与本轮证据见[交互规范规格](../../.scratch/interaction-policy/spec.md)。

## 可执行检查

用户已要求将 `@shadcn/lint` + Oxlint 从条件接入提升为 S1 正式 GUI 的必备检查。Biome 继续负责通用 lint/格式化，TypeScript 负责类型检查；Oxlint 限于设计系统规则，不复制通用 lint 或引入 ESLint/Prettier。

2026-09-27 查阅[官方说明](https://github.com/shadcn-ui/lint)：当前面向 Tailwind v4，支持 Oxlint，列有原始颜色、任意值、组件重绘、内联样式、未知类和动态类检查。接入时核实并锁定 Tailwind、Node、Oxlint 和插件兼容版本；该资料不是本项目已运行证明。Tailwind 的[主题变量机制](https://tailwindcss.com/docs/theme)可承载语义工具类映射。

S1 配置并以真实正反例验证以下目标，具体选项按固定版本核实：

- `no-raw-colors`：业务视图不直接选原始色板/字面颜色。
- `no-arbitrary-values`：拦截绕过 token 的视觉值；官方组件中的几何计算、CSS 变量引用及合理结构表达式按固定版本配置窄例外，不机械禁止所有方括号语法。
- `no-restyle`：识别本项目组件导入路径并限制调用方覆盖，只开放约定的布局能力。
- `no-inline-styles`：限制绕过类与 token 的手写样式；动态测量、定位等由适配层按属性声明例外。
- `no-unknown-classes`、`require-static-classes`：核实生成能力，避免 AI 拼接不可分析的动态类。

组件内部可以定义自己的变体，不在共享组件目录无差别关闭全部检查；仅按需要调整重绘限制，颜色/token 约束仍有效。组件别名、cn/cva 等实际写法必须被识别。

接入须验证 CSS Modules 导入类、全局自定义类和上游 cn-* 类不会被误判为未知 Tailwind 类；必要时按已识别来源配置，不全局关闭检查。不得为让 lint 通过而把清楚的 CSS 改写为冗长工具类。

这些规则不证明全部 CSS/动态数值都受控，也不自动验证 token 语义、对比度或布局。接入时列出 CSS 文件、直接变量定义、动态几何等覆盖缺口；用最小针对性检查和评审覆盖，不先自研通用 lint 平台。禁止业务目录私建主题/密度变量或以任意 CSS 绕过 JSX 检查。

设计检查接入本地统一检查命令及 CI（建立 CI 时），违规返回失败，不是仅输出警告。例外记录具体文件/属性、理由、替代评估和验证样本，不能扩大为目录级随意覆盖。修改规则本身也需要审查，lint 通过不能证明规则未被放松。

## 随切片验收

以下 S1 双密度验收保留为历史依据，2026-10-06 起新工作按下方默认紧凑基线验收，不重写旧证据：

S1 当时除草稿功能外，要求交付最小 token 源、normal/compact 映射、实际组件识别与可运行的设计检查：

1. 一个符合规则的组件组合通过；原始颜色、任意间距及调用方改内部样式的负样本确实失败。检查样本不进入生产视图。
2. 仅修改集中 primary 源值，分别使用 Tailwind、CSS Modules、普通 CSS 的代表性消费者同步更新，无须改写调用处或复制数值；无关语义色不被误改。再验证其他主题角色在按钮、输入、面板与交互状态中的映射；不修改业务页面。
3. 仅切换全局密度入口，已有控件和布局联动；无截字、遮挡、焦点丢失或点击区域错误。
4. 代表性的深浅主题与两种密度真实 GUI 检查；样本随组件接入增长，无需先建全组件 Gallery。

当前切片检查新增或变更组件的 light/dark、默认紧凑布局、交互状态、焦点和布局；复用既有 lint 正反例，只在映射、组件合同或规则变化时重测相关样本。代表性组合覆盖同一 Button 出现在导航、工具栏、配套动作与业务表单中的一致性；检查角色关系、可用操作和主题传播，不写只复述 CSS 数值的测试。修改集中主操作/辅助文字来源后，相关消费者及状态同步更新，邻近独立角色保持正确。

流式内容和弹层按实际风险检查。Monaco/Diff 的映射已随 S4 交付（`src/modules/files/renderer/editor/monaco-viewer.tsx` 从 token 构造主题）；存量密度监听随取消切换按实际影响处理，后续终端等在各自切片补适配。密度切换历史测试不是当前新布局的必跑矩阵，不因为收敛密度删除仍有价值的主题、几何、输入与恢复检查。

这些通过后才能声称在所测范围内具备统一换肤和密度能力；S1结果已记录，不能外推为所有未来组件均已验收。

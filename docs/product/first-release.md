# 首版基础方案收敛

本页维护首版验收、Composer 和变化记录的产品基线，不维护实施进度。2026-09-25 用户要求先收敛方案、再动手，并对审查七项逐一回复，采纳主要建议并授权工程补齐；当时仅做文档、源码核实和设计，不构成后续禁止实施。首版范围和工程行为由 D-23–D-26 与[基础契约](../architecture/foundation-contracts.md)收敛；2026-09-26 的 D-32–D-35 确认 Base UI、最小 Tiptap、SQLite 与 TypeScript 范式，其他候选状态不变。已确认边界见[决定登记](../decisions.md)，最终需求见[产品需求](requirements.md)，授权、实际验证和用户试用读取[切片记录](../README.md#工作记录)。

## 1. 首版是一个什么交付

首版 M2 为 macOS 本地开发客户端：无需安装 OMP CLI，已有配置直接使用，新用户可由 GUI 完成原生配置；可打开本地项目、创建/切换/恢复 Thread、输入需求、处理 Agent 交互、检查项目文件和代码差异，并继续工作。不是只用于验证 API 的演示壳，也不是一次交付最终全集。

- 不包含自由分屏、完整 IDE 扩展/调试体系、完整通用 Git 客户端。

### 初始化接入方案

先由包内 Runtime 在原生配置上下文查询配置、认证、模型和能力；已有可用状态直接进入。新用户 GUI 按“OpenAI 账户登录或 DeepSeek API key → 完成认证 → 选择模型/必要默认设置 → 检查并开始”组织，允许取消与重试。可选搜索、语音、主题等不作为开始文字会话的额外前置要求。

这不是照搬 TUI 屏幕。v18.3.0 的 `createSetupHost` 已把配置/模型/认证作用与 TUI 场景连接，说明可复用职责；它依赖 TUI context，不是已可直接调用的桌面 RPC。必须优先调用可用原生接口，必要时暴露薄适配，不重写认证协议或配置合并。不能用 TUI 的 setupVersion 是否写入作为唯一可用性判定，也不擅自替 TUI 标记全部向导完成。

## 2. Composer：最小 Tiptap 与项目业务扩展

### 已确认路线与原因

2026-09-26 用户确认 D-33：采用最小 Tiptap，复用编辑器扩展组织与 React 接入，以项目业务扩展实现结构化引用、附件关联、草稿和原生提交适配。按实际输入需要注册编辑、历史与键盘能力，保留自有呈现，不默认引入完整工具栏或协作服务。

该决定取代 P-02 的“直接 ProseMirror 优先、Tiptap 有条件对照”。必要的底层定制通过 Tiptap 的扩展和 @tiptap/pm 完成；不并行建设第二套 Composer，不默认 fork 上游。此前方案的可控性理由与维护成本比较保留在[研究](../../.scratch/product-requirements/composer-research.md)，不再作为待定选型；真实 IME、引用交互与性能仍须验证。

### 单一所有权

| 数据 | 所有者 | 约束 |
| --- | --- | --- |
| 文字、换行、引用节点、选区、撤销历史 | Tiptap 编辑器实例 | React 不每次流式更新都重建 editor；不另存第二份可写文字正文 |
| 附件内容、预览、处理任务 | App 附件服务 | 编辑器仅持 ID；二进制不进入撤销栈；删除引用不等于立刻删除其他草稿仍引用的内容 |
| 每 Thread 的持久草稿 | App 草稿存储 | 使用带版本的业务 DTO，不把编辑器内部 JSON 作为全应用/OMP 的永久协议；本地编辑快照由适配层处理 |
| 发送中的内容包 | 宿主提交适配 | 一次提交冻结内容、附件和引用，随后编辑草稿不能改动已提交内容；映射到 OMP 支持的消息/图片/资源形式 |
| 接受后的消息与队列 | OMP | 不把 GUI 草稿清除当作 Runtime 已接受；结果不明时重同步而非自动重复提交 |

### 2026-09-27 用户明确的输入体验要求

目标是达到用户熟悉的 Codex App 输入体验，并改善其特殊路径检索、响应速度和混合多媒体操作。以下为用户场景要求，不是现有组件或性能已验收的结论。

| 用户操作 | 必须获得的体验 | 验证要点 / 待明确 |
| --- | --- | --- |
| 输入或粘贴长短文本 | 保持可编辑；不能因粘贴而变成无法修改的块 | 长短文本、多段与混合粘贴后都能定位、修改、选择、撤销和重做；具体折叠样式未定 |
| 从网页或文档粘贴带结构的内容 | 普通粘贴尽量保留标题、列表、表格等结构，转换为可编辑 Markdown；另提供“粘贴为纯文本” | 2026-09-27 用户明确采纳；按剪贴板实际提供的信息转换，不宣称还原所有来源格式。验收标题层级、列表、表格、链接、后续编辑及撤销重做；Markdown 样式直接渲染仍可后置 |
| 使用熟悉的桌面编辑操作 | 流畅的 undo/redo、上下与首尾光标移动、快捷键选区及中文输入 | 在真实 Electron 编辑界面测 IME、跨引用节点导航、长文本和同时流式输出；采用 Tiptap 不等于这些行为已经通过 |
| 拖入或粘贴多媒体/附件 | 依据 MIME 等输入信息进入相应处理，附件有实际内容承载，不只剩路径 | 复用私有内容存储与冻结合同；类型未知、损坏或不支持不能误报成功，不只凭后缀判断 |
| 查看和整理已附加材料 | 输入区上方有多媒体预览区，随草稿更新，可点开查看、缩放和调整附件顺序；附件提供相应呈现 | 用户确认基础查看/重排与图片编辑两个层级都需要；不扩展为完整文件管理器 |
| 发送前处理图片 | 可裁剪、旋转、画框/标注，并将处理后的图片用于发送 | 用户确认第二层级需求，随后明确作为首版后的增强；具体工具细节待细化。原件/派生内容沿用附件合同，验收核对预览与实际送出版本一致 |
| 通过 @ 找文件 | 触发语法与实际路径字符分开处理，包含 @ 的路径可正常检索和选择 | 用户例子 @message@List；验证前导/中间 @、连续查询的迟到结果、真实项目规模与响应延迟；具体查询语法/索引方案待实现 |
| 附件存在时切换模型 | 显式管理草稿内容、附件准备与模型兼容性变化，预览与可发送状态保持一致 | 沿用基础契约：内容不静默丢失，目标变化重新预检，不支持的表示阻止发送并提供显式处理选项；切回模型、准备中切换及旧结果迟到均须验证 |
| 粘贴超链接 | 动态快速识别预设网站：名单内用网站品牌图标（如 GitHub）加链接，其他网站用地球图标加链接 | 链接识别与图标展示从最初输入方案及后续 spec/ticket 就应明确，不列为用户允许后置的增强。完整 URL 保留，不能为展示改变实际目标 |

用户提出用状态机处理上述组合。按 D-29/D-30 理解为显式状态及转换规则，继续使用既有 TypeScript 方案，不引入 XState；编辑撤销仍归编辑器，附件与模型预检属于无头功能，不把所有状态塞进单个 UI 状态或巨型状态机。图片操作两层均已确认为目标；后续访谈明确 M2 完成查看/缩放/重排，裁剪/旋转/标注作为首版后增强。

2026-09-27 用户纠正：可以后置的是整个输入框内 Markdown 样式的直接呈现，例如 H1、H2、表格；不是链接识别或图标展示。前期允许编辑 Markdown 源文本，不要求已具备标题/表格的所见即所得排版。输入体验应从方案、spec 和后续 ticket 明确描述，不能只写“对标 Codex App”或把这些要求遗漏到实现后补。

网站名单用于展示识别，不是访问权限或可信网站名单。工程上优先本地解析 URL 的实际主机名并按明确域名规则匹配；仅为识别 GitHub 等网站不需要访问链接、下载 favicon 或预抓正文。品牌与通用图标经自有 Icon Layer 接入，遵守 D-31；品牌标识保留身份规范，不为此引入第二套通用图标库。此处确认的是输入展示，未授权新增自动抓取网页内容的产品行为。

### 输入行为规则

- 2026-09-27 用户确认发送方式可切换：默认 Enter 发送、Shift+Enter 换行；另一种为 Enter 换行、⌘Enter 发送。点击放大按钮展开编辑区后，自动采用第二种。实现细化：展开状态临时覆盖当前编辑区的生效模式，不改写持久偏好；收起后恢复用户设置，显示当前发送快捷键。IME 组合期间及候选确认不触发发送，@ 菜单打开时 Enter 先确认候选，优先于发送/换行规则。
- 放大/收起属于编辑视图变化，应保留当前文字、附件、选区和撤销历史，不能因切换编辑模式清空草稿或重置编辑历史。验收覆盖默认/自定义模式、展开/收起、中文候选及 @ 候选确认，检查实际行为与快捷键提示一致；具体放大布局未定。
- 引用显示路径与行号；建议选区在附加时保存原文，@ 文件在发送准备阶段读取并冻结内容。内容变化时保留来源并提示，不把旧行号装作最新定位。该捕获语义已随本轮第 4 项采纳，详见基础契约 §4。
- 发送前等待必要附件处理完成；失败项明确定位，用户可以重试/移除，禁止静默漏发。大小/类型/模型限制由能力检查返回，不硬编码“所有 PDF 都可直接发给任何模型”。
- 按[提交交接合同](../architecture/foundation-contracts.md#2-提交交接b2)先持久保存冻结原文，再将关联的调用 ACK 与对应草稿消费标记一起持久化，才清理对应版本草稿（2026-09-28 用户修订 D-24）。首次 success 不代表业务接受或完成，原文以可查看/复制的发送记录保留。后续失败保留原提交内容，提交过程中新增的输入保留。切换 Thread、窗口刷新、失败重试均不串草稿。
- OMP 原生输入支持与 GUI 接受类型分开。v18.3.0 RPC prompt 明确有 message/images，不据此假定任意文件/PDF 都有通用二进制字段；优先核实原生引用/读取/转换路径。

### 开工前与实现后的验证分开

Composer 功能实现授权包含必要的隔离样本验证，无需再申请一次阶段授权；样本不冒充正式产品源码。若真实证据表明选定路线不能满足合同，记录问题、影响和替代方案后按决定变更规则处理。2026-09-26 的文档阶段没有编写原型，后续覆盖读取所属切片。

样本覆盖：系统中文输入法（拼音候选确认）、英文、多段输入、@ 查询过期结果、节点边界选择/删除/撤销、混合粘贴、多附件失败、提交中切 Thread、失联后的重复提交风险、恢复与流式消息同时更新。通过真实 Electron GUI 操作验证 IME，模拟键盘测试不能替代它。性能记录机器、版本、输入/消息规模、输入延迟和内存变化；不得先编造一个达标数字或用静态截图代替行为验证。

## 3. 变化记录：先明确证据，再展示 Diff

### 三种东西分别呈现

| 视图/来源 | 比较对象 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| Git 当前变化 | HEAD ↔ index；index ↔ 工作区；未跟踪文件另列 | 当前仓库状态 | 不是自动等于本次 Agent 的修改 |
| 工具修改证据 | 原生工具实际返回的 patch/结果，关联 toolCallId 和会话 | 工具报告过什么；有可靠前后文本时可画 Diff | 调用参数不是修改成功证明；可能缺前文或含截断，不覆盖任意 shell/后台/外部修改 |
| Run 期间观察到的变化（后续） | 明确的起止采样与覆盖清单 | 在该观察区间发现的差异 | 不自动证明作者，也不代表文件系统原子快照 |

2026-09-25 用户已确认首版交付前两种，完整 Run Changes 和逐次修改归属后续接入（D-20）。不能用“全部 AI 改动”给它们命名。工具没有可靠前文时展示结果与路径，并能打开该文件当前 Git 差异，但清楚标注这是另一来源；不能用 HEAD 当作该工具执行前内容拼出虚假的操作 Diff。非 Git 项目仍可查看文件和工具结果；没有基线就不伪造完整历史差异。

Agent Changes 是后续按执行来源组织的产品视图，不能简单等同工具路径集合或 Run 区间差异。同一文件被用户和 Agent 同时修改时，不把整份文件归为 Agent。这个边界从首版就保留。

### 原生证据核实（固定 v18.3.0，源码检查，未运行实验）

- `AgentEvent` 包含 agent/turn/tool 开始结束；工具事件有 toolCallId、参数和结果。`agent_end` 在 Session 扩展里有可选 isTerminal，false 表示异步后续还可能恢复。不能把一次模型 turn 或任意 agent_end 都当作产品 Run 完成。
- `RpcCommand` 中已检查的类型未提供通用全文件变更账本/持久前后快照导出命令；这是所检查接口范围的结论，不宣称整个 OMP 无其他能力。
- `EditStore` 是会话持有的原生编辑快照，read/search/write 等用于 hashline 标记和编辑；不能由其存在推导 GUI 已获得持久、完整的改动历史。
- `write` 的普通成功结果可只含 resolvedPath/madeExecutable/diagnostics，没有完整 before/after；内部可能经写后处理产生 finalContent，不能直接把输入参数当最终磁盘内容。
- checkpoint/rewind 的实现与记录围绕会话上下文，不能将工具摘要中“git-based checkpoint”一句当成磁盘恢复保证。

### 组件边界与数据合同建议

1. Git 读取服务返回仓库身份、HEAD/index/worktree 的明确来源和捕获时点，区分新增、删除、重命名、二进制、未合并、子模块与无 HEAD。利用成熟 Git 实现，不改 index、不创建临时提交、不 stash 用户修改来采样。
2. 工具证据适配层保存会话/实例代次、toolCallId、原生结果来源及错误/截断状态。先复用 OMP 原记录，仅在实际无法恢复时保存必要补充证据，不另造执行历史。
3. Monaco Diff 仅接收明确的左右内容与来源标签，不读 Git、不推断作者、不决定回退动作。缺失内容、二进制或权限失败提供对应说明，不以空字符串伪装空文件。
4. 活动 Diff 更新前后检查版本变化；文件/索引在读取期间变化时重读或显示陈旧状态，不宣称跨多文件一致快照。编码与换行变化保留；大文件/截断必须显式标注。
5. 首版不引入隐藏 Git 分支、全工作区快照库或文件系统拦截器。未来如需 Run Changes，再评估原生接口与有边界的采样，不提前搭建持久化平台。

### 为 Run / Review / Revert 留位置，不提前承诺能力

未来数据应能携带 Thread、执行区间、触发输入、工具证据、采样时间及覆盖缺口；具体实体数量和存储方式等需求进入该阶段再定。可建议 Run 为宿主观察的一个执行周期，但不在本轮确定它与 prompt/turn/agent_end 一一对应；排队追加、干预、子 Agent 延迟返回和崩溃都必须先核实。

Review 的目标应关联具体内容版本，内容改变不能继续沿用“已查看”而不提示。Revert 要明确操作对象、目标版本、当前版本前置条件、并发修改和失败处理后才能启用；目前不选 Git 命令、不写实现。OMP 原生会话回退继续遵守既定定义，不承诺磁盘恢复。

### 必验反例

- 启动前已有用户改动，Agent 只改一行：Git 视图显示全部当前变化，工具证据不能把已有改动算成 Agent。
- Agent 通过 shell 或子 Agent 改文件：不能只监听 edit/write 后宣称改动完整。
- 外部编辑器并发修改：标明归属不可确定，不允许据此做自动回退。
- 新文件/删除/重命名、未暂存/已暂存并存、初始仓库无 HEAD、冲突状态：两侧来源准确。
- 只读项目、无 Git、超大/二进制文件、符号链接越界：给出真实边界，不破坏项目；明确批准范围外的读取按[基础契约 §5](../architecture/foundation-contracts.md#5-最小权限与信任b5)处理。
- 执行中崩溃/重连：缺失基线就是缺失，不能用恢复时磁盘状态倒填运行前快照。

### 多 Thread 提醒策略（2026-09-27 用户确认）

- 后台 Thread 需要用户回答或执行失败时，侧栏明确标记并给出不抢焦点、可点击进入的应用内提醒；App 不在前台时，通过已获授权的系统通知提醒。系统通知未授权或不可用时仍保留应用内状态，不把通知送达当成用户已处理。
- 正常完成默认仅标记完成和未读，不主动弹提醒；用户可开启完成通知。
- 不自动切换 Thread，不夺走当前输入焦点。提醒关联所属 Thread，点击定位到对应问题或结果；问题已经处理或请求已失效时显示实际状态，不提交旧回答。

该策略随 M2 多 Thread 体验验收。Host/执行模块提供真实状态，Main 负责系统通知与无窗口时的通知协调，Renderer 呈现侧栏和应用内提醒；提醒不成为新的执行事实来源。验证前后台切换、关窗、重复事件、过期交互、系统通知不可用和通知点击定位。通知偏好属于 App 设置，不写入 OMP 原生配置。

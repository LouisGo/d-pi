# OMP Desktop · V1 技术架构方案

> 2026-09-24 后续调整：本文件保留完整 V1 的规划背景；当前优先级改为先验证 Runtime 能力复用，见 [最新可行性结论](runtime-feasibility.md)。用户明确最终应用应携带 OMP，无需用户另行安装；下文“缺失时再下载安装”的初始化路径尚待按此目标修订，不是当前交付承诺。

**定位：为完整的 OMP Runtime 提供一个更好用的桌面交互入口，而不是重新实现一个 Agent。**

首版以 macOS 为优先平台，支持多个会话并发运行；已有 OMP 用户直接复用环境，新用户在 GUI 内完成安装与配置。架构从第一天采用 `utilityProcess`，但不提前建设跨平台、跨 Runtime 的通用框架。

本文定义完整 V1 的目标架构，不代表下一次实现必须一次覆盖全文。交付按第四节的阶段计划推进；阶段内暂未提供的功能不能被当作 V1 已完成。

核心分工固定为：

> **Electron Main 管应用；SessionHost 管连接与同步；OMP 管执行；React 管体验。**

# 一、技术选型

## 1.1 基础技术栈

| 范围       | 选型                                              | 在项目中的职责                                      |
| -------- | ----------------------------------------------- | -------------------------------------------- |
| 桌面宿主     | **Electron**                                    | 窗口、系统集成、安全边界、进程监督                            |
| 前端       | **React + TypeScript**                          | 输入、对话、工具卡片、详情与设置界面                           |
| 客户端状态    | **Zustand**                                     | 会话展示镜像、界面状态、局部订阅                             |
| 异步查询     | **`@tanstack/react-query`**                     | 模型列表、会话目录、配置状态等查询与缓存                         |
| 样式与组件    | **Tailwind CSS + 自有组件层**                     | 自己定义设计变量、组件 API 与视觉；按需借用 Radix 等底层交互              |
| 数据校验     | **Zod**                                         | 跨进程消息、配置、外部数据的运行时校验                          |
| 构建       | **electron-vite + Vite**                        | Main、preload、Renderer、utility process 的开发与构建 |
| 包管理      | **pnpm**                                        | 依赖管理、锁文件与统一脚本                                |
| 质量工具     | **ESLint + Prettier + TypeScript strict**       | 代码规范、类型检查、模块依赖边界                             |
| 测试       | **Vitest + React Testing Library + Playwright** | 单元、组件、协议集成与桌面端冒烟测试                           |
| 打包       | **electron-builder**                            | macOS 应用与安装包                                 |
| Agent 接入 | **本机 OMP + stdio RPC**                          | 复用完整 OMP，优先验证并使用 `rpc-ui`                    |

这里将你说的 `@tanstack/query` 落到 React 对应的包 **`@tanstack/react-query`**。electron-vite 已提供 utility process 独立入口的构建支持，不需要自行搭建多进程打包系统。([TanStack][1])

自有组件层以 shadcn/ui 的源码与组织方式为参考，Beautiful UI 作为重要视觉与交互参考并可选择性复用素材。Base UI 不作为后续默认组件底座；已存在的使用属于存量代码。候选库的理由、上游入口与接入条件见 [前端选型记录](frontend-library-radar.md)。

**编辑器、Diff、虚拟列表、复杂 Markdown 渲染方案继续待定。**先建立组件边界和真实测试样本，不提前选库，也不先写自研替代品。

## 1.2 版本策略：使用最新稳定版，但构建必须可复现

建仓时解析各依赖的 **latest 稳定版本**，随后记录精确版本并提交锁文件。CI 使用冻结锁文件安装；升级通过明确的依赖更新提交进行，而不是每次构建重新解析 `latest`。pnpm 的 `--frozen-lockfile` 就用于阻止安装过程中意外改变依赖解析结果。([pnpm][2])

OMP 单独管理兼容性：

**GUI 依赖可以统一升级，本机 OMP 不可以被 App 擅自升级。**

项目需要记录“已验证 OMP 版本、协议能力、初始化接口和已知限制”。已有兼容版本直接使用；不兼容时说明原因并提供 GUI 内的处理入口，不静默替换用户环境。

# 二、项目基建

## 2.1 独立仓库、单应用，不先拆成平台型 monorepo

推荐目录：

```text
src/
  main/                     Electron 主进程
    windows/
    process-supervisor/
    native-services/

  preload/                  受限的系统与业务接口

  host/                     utility process：SessionHost
    runtime/                OMP 进程、RPC、请求管理
    sessions/               会话注册、镜像、订阅与同步
    bootstrap/              环境发现、安装、认证与配置
    storage/                App 自有元数据、草稿与缓存
    diagnostics/            日志、错误归类、诊断导出

  renderer/
    app/                    入口、主题、Provider
    features/
      onboarding/
      workspace/
      conversation/
      settings/
    components/
      ui/                   自有基础组件，可按需使用底层交互 primitive
    stores/                 Zustand
    queries/                TanStack Query
    client/                 preload / MessagePort 客户端

  shared/
    protocol/               自己的跨进程消息定义与 Zod schema
    types/                  可跨进程传递的数据类型

helpers/
  omp-config/               按需运行的 Bun 配置助手

tests/
  unit/
  contract/
  e2e/
  fixtures/

docs/
  architecture.md
  omp-compatibility.md
  adr/
```

**目录表达责任，不代表每个目录都要成为独立包。**

`shared` 只放协议、数据结构和少量纯函数，不能成为所有模块都往里塞代码的公共仓库。

## 2.2 从第一天约束依赖方向

通过 TypeScript 配置和 lint 规则落实：

| 区域          | 允许依赖                   | 禁止依赖                   |
| ----------- | ---------------------- | ---------------------- |
| Renderer    | React、前端库、共享类型、受限客户端   | Node 文件系统、进程管理、OMP SDK |
| preload     | Electron 桥接、共享协议       | Agent 执行逻辑、会话业务        |
| SessionHost | Node API、共享协议、OMP 协议适配 | React、DOM、窗口组件         |
| Main        | Electron 系统能力、进程监督     | 对话内容处理、Agent 调度        |
| 配置助手        | 经验证的 OMP 配置与认证 API     | GUI 组件、自己的 Agent Loop  |

这样做的目的很实际：**不能因为某个组件需要一点数据，就顺手跨过进程边界 import 一整个后端模块。**

## 2.3 测试重点不是组件覆盖率，而是连接是否可靠

约定统一的开发、检查、测试和打包脚本。CI 至少执行：

**类型检查 → lint → 单元测试 → 协议测试 → 构建 → 桌面冒烟测试。**

测试分成两条线路：

**可重复的模拟线路。**使用假的 OMP 子进程，覆盖 UTF-8 分片、半行 JSON、超大消息、延迟响应、进程退出、取消和窗口重连。日常 CI 不依赖真实模型、不产生模型费用。

**真实的兼容线路。**使用已锁定的 OMP，在隔离的配置目录和测试项目中验证认证、工具、原生会话、并发与退出。不能只验证“能收到一句模型回复”。

Playwright 的 Electron 支持目前仍标注为实验性，因此将它用于关键冒烟流程；进程与协议正确性不能只依赖这层测试。([Playwright][3])

# 三、架构设计

## 3.1 总体结构

```text
┌─────────────────────────────────────────────────────────┐
│ Electron Main                                           │
│ 窗口、系统能力、进程监督、通信通道建立、应用退出           │
└───────────────┬────────────────────────┬────────────────┘
                │                        │
          创建窗口与桥接             启动并监督
                │                        │
                ▼                        ▼
┌──────────────────────────┐   ┌──────────────────────────┐
│ Renderer                 │   │ Utility Process          │
│                          │   │ SessionHost              │
│ React                    │   │                          │
│ Zustand                  │⇄⇄│ OMP 连接与请求管理       │
│ TanStack Query           │   │ 会话镜像与订阅同步       │
│                          │   │ 用户交互请求交接         │
│ 输入 / 对话 / 卡片 / 详情 │   │ 初始化 / 本地元数据      │
└──────────────────────────┘   └────────────┬─────────────┘
       经 preload 建立的 MessagePort        │
                                           ├─ RPC → OMP 会话 A
                                           ├─ RPC → OMP 会话 B
                                           └─ 按需 → 配置助手
```

正常业务通信走 **Renderer ⇄ SessionHost**。Main 负责建立与授权通道，不转发每一个文本增量。Electron 官方支持通过 MessagePort 建立这类跨进程通信。([Electron][4])

SessionHost 使用 Node.js；OMP 保持独立运行。OMP 当前 SDK 面向 Bun，不能直接假设能够嵌入 Electron utility process。utility process 自身不提供普通可写 stdin，并不妨碍它在内部启动具有 stdin/stdout 管道的 OMP 子进程。([Electron][5])

**不增加 HTTP Server，不把 stdio 转成 WebSocket，也不让 TUI 参与 GUI 渲染。**

---

## 3.2 中间层的厚度：执行语义薄，会话服务完整

SessionHost 必须承担以下职责：

| 职责     | 具体做什么                 | 不做什么                |
| ------ | --------------------- | ------------------- |
| 运行环境连接 | 启动 OMP、解析协议、关联请求、发现异常 | 重写模型调用与 Agent Loop  |
| 会话管理   | 维护会话与进程对应关系、接续已有会话    | 建立另一套 Agent 会话格式    |
| 状态同步   | 维护运行镜像，提供快照和增量        | 自行决定工具成功、任务完成       |
| 交互交接   | 转交提问、确认、输入和取消         | 默认同意未知请求            |
| 初始化    | 发现环境、安装、认证、配置验证       | 重写供应商认证协议           |
| 桌面元数据  | 草稿、最近项目、阅读位置、诊断缓存     | 持久化另一份可写的 Agent 上下文 |

判断边界的方法很简单：

> **OMP 决定发生什么，SessionHost 保证 GUI 正确知道发生了什么，并能把用户操作送回去。**

例如“请求已接受”与“任务已结束”必须区分。OMP 当前 RPC 的 `prompt` 可以先确认接收，再通过后续事件报告执行；不能因为请求返回成功，就把会话标记为完成。

### 执行中输入（2026-09-24 用户确认）

阶段 1 即支持：空闲时正常发送；执行中默认排队追加，并提供独立、明确的“干预当前执行”入口。排队追加交给 OMP 原生队列处理；干预优先使用原生 steering 能力，不隐式转换为强制杀进程或先停止再重发。

GUI 区分提交中、已接受／待处理与已实际处理，不能把接收确认当成干预已生效。具体消费时机、顺序及停止对队列的影响须通过目标 OMP 版本原型确认；Host 不另建一套 Agent 调度器，断连后不自动重放结果不明的输入。

## 3.3 多会话并发：一个 SessionHost，多个独立 OMP 实例

首版采用：

> **一个活跃顶层会话对应一个 OMP 进程；一次会话内的连续对话复用该进程。**

不是每次发消息启动新进程，也不是通过一个 OMP 进程反复 `switch_session` 假装并发。

每个实例绑定自己的工作目录、原生会话、请求表和事件流。OMP 内部的子 Agent 仍由 OMP 管，GUI 不重复调度。

需要明确四条规则：

**浏览历史不等于启动 Runtime。**历史列表和只读查看尽量不唤醒执行环境。

**切换标签不终止任务。**后台会话继续被 Host 接收和维护；界面主要订阅其状态摘要，需要查看时再取得详细快照。

**回收不能打断工作。**执行中、等待用户输入、仍有原生后台活动的会话不能因为“不在当前标签”就被回收。

**进程隔离不等于文件隔离。**两个会话使用同一工作目录，仍可能互相修改文件。GUI 必须显示这种共享关系并在并发执行前明确提醒；不擅自创建 worktree，也不承诺自动解决冲突。同一个原生会话由两个执行进程同时写入，不属于首版支持用法。

这个结构有成本：多个 OMP 实例会带来各自的运行资源。先实现清楚的实例生命周期和资源可见性，不以“无限并发”为目标。

## 3.4 状态只设一份权威，但允许必要的镜像

| 数据                | 权威归属            | GUI 如何使用              |
| ----------------- | --------------- | --------------------- |
| 原生会话、分支、上下文、工具结果  | **OMP**         | 读取、建立展示镜像，不反向重建上下文    |
| 当前连接、待响应请求、临时流式尾部 | **SessionHost** | 窗口重连时同步               |
| 输入框撤销栈、光标、选区      | **输入组件**        | 不跨进程同步每次编辑动作          |
| 草稿、面板布局、阅读位置      | **GUI 产品状态**    | 必要时由 Host 写入 App 数据目录 |
| 模型列表、配置摘要、会话目录    | **各自原始来源**      | TanStack Query 缓存查询结果 |

OMP 的持久会话与模型当前上下文并不是同一个概念。GUI 应沿用原生记录，不把界面里的消息数组当作重新启动 Agent 的完整材料。

### Zustand 与 TanStack Query 的分工

**Zustand 管正在变化的展示状态。**消息、工具卡片和会话摘要按 ID 组织，组件只订阅需要的实体。OMP 事件先由 Host 解释，Renderer 不再维护另一套不同的协议语义。

**TanStack Query 管“请求一次获得结果”的数据。**例如模型列表、历史目录、配置摘要和文件元信息。查询函数可以调用本地 IPC Promise，不要求有 HTTP 服务。([TanStack][6])

**同一条实时消息，不同时由 Zustand 和 Query Cache 各维护一份可写正文。**发送、停止、回答问题等有副作用的操作，也不能套上默认的自动重试。

App 自有元数据首版使用带 schema 版本的轻量文件存储，集中写入、原子替换；不为草稿和布局先引入一套业务数据库。

## 3.5 同步协议：快照接入，增量更新，缺口重建

自己的 GUI 协议只包裹必要信息：请求 ID、会话身份、Runtime 实例代次、更新序号。**这些属于我们自己的通信信封，不是臆造 OMP 已经具有相同字段。**

窗口接入时，Host 提供一个版本一致的快照，再发送其后的增量。发现序号缺口或实例已经替换，就重新同步，不能把旧实例的响应写进新会话。

对 OMP 协议本身，要正确处理协商、分片与体积限制。当前 RPC 已存在超大消息分片和有状态的历史分页机制，不能把一次 stdout `data` 回调当作完整 JSON，也不能在分页失败后把不同快照拼起来。

性能策略落实在具体位置：

**Host 合并连续输出，Renderer 精准更新组件。**不要每个增量都跨进程发送整份会话，也不要每次都扫描完整历史。

**批处理保留顺序。**工具开始、需要用户回答、取消与结束等事件到来时，先处理此前的文本缓冲，再发布后续状态。

**后台降低展示频率，不停止读取 OMP 输出。**缓存、重放队列和大输出都要有上限；超出范围走重新同步或按需读取，不能无限堆内存。

utility process 中使用自己的定时调度，不依赖 Renderer 的 `requestAnimationFrame`。界面隐藏或刷新，不应影响运行侧接收事件。

## 3.6 全 GUI 初始化：一条独立入口，不混进日常 Agent 执行

这是 A 方案带来的明确新增职责。

### 已有用户：发现并复用，不重新“初始化一遍”

启动时自动发现 OMP 可执行文件、版本、有效配置目录、工作目录与模型可用状态。环境解析必须考虑从 Finder 启动和从终端启动的差异，不能只检查 Electron 当前的 `PATH`。

配置目录不硬编码为 `~/.omp/agent`。OMP 支持通过 `PI_CODING_AGENT_DIR` 重定位，也提供 `omp config path` 和结构化配置查询。

正常路径是：

**发现兼容 OMP → 读取已有有效配置 → 直接进入工作区。**

只有确实缺失、失效或不兼容的部分才进入修复界面。不自动覆盖配置，不复制一套凭据，不因为 GUI 首次启动就重新选择模型。

### 新用户：安装、认证、选择模型、验证，全程 GUI

流程固定为：

**检测环境 → 安装缺失运行环境 → 添加凭据 → 选择模型 → 验证 → 打开项目。**

缺少 OMP 时，App 在用户确认后安装到用户级管理目录；不要求 sudo，不强制安装 Homebrew，不修改已有全局 OMP。下载物校验来源与完整性，安装失败可以重试，不留下被误认为可用的半成品。

OMP 官方同时提供独立安装方式和 Bun 包分发，我们的安装器负责封装经过验证的一条路径，而不是让用户复制终端命令。

### 认证通过按需启动的 `ConfigHelper` 完成

普通 RPC 目前会拒绝需要秘密输入的部分登录流程，所以不能只用 RPC 实现完整首次配置。

配置助手运行在独立 Bun 环境，通过与目标 OMP 版本匹配的原生配置和认证 API 工作：

```text
GUI 配置表单
    ⇅
SessionHost / Bootstrap
    ⇅
Bun ConfigHelper
    ⇅
OMP 原生认证与配置接口
```

它把授权 URL、普通输入、秘密输入、进度和取消转交 GUI；浏览器授权由 Main 打开系统浏览器。OMP 原生认证接口已经提供 `onAuth`、`onPrompt` 和登录入口，具备这种接入基础。

**ConfigHelper 不创建另一套 Agent，不参与日常工具执行。**只在初始化、修改认证或相关配置时启动。

凭据与配置规则：

* 凭据通过 OMP 原生接口保存，不直接修改内部数据库；设置优先使用原生配置接口，避免整文件覆盖。
* 秘密输入只短暂存在于表单和必要通信中，不进入持久化 Zustand、诊断日志或查询缓存。
* 不把“原生保存”宣称为额外的 Keychain 保护；这里沿用 OMP 的凭据存储边界，不再复制另一份。
* 配置助手与目标 OMP 的版本兼容必须验证，不能用任意最新 SDK 操作旧版本存储。

**“全 GUI”是体验要求，不是对所有供应商与扩展的无条件兼容承诺。**发布前，每条标为支持的认证路径都必须实际完成过；不支持时在 GUI 内说明，不能偷偷降级为“请打开终端”。

另外，当前 `rpc-ui` 的启动行为包括禁用 PTY，且协议模式有自己的默认设置处理。因此“复用已有配置”不能被宣传为“所有 TUI 行为逐项相同”；这些差异必须进入兼容测试。

## 3.7 故障与安全边界

| 场景             | 产品行为                                 |
| -------------- | ------------------------------------ |
| Renderer 刷新或崩溃 | Host 与 OMP 继续存活；新窗口重新获取快照与订阅         |
| 单个 OMP 实例退出    | 只把对应会话标记为中断；其他会话继续                   |
| SessionHost 退出 | Main 告知所有受影响会话，处理旧进程、重建 Host；不承诺原地续跑 |
| 关闭窗口 | 保留 Main、Host 与 OMP，任务继续；从 Dock 重新打开窗口接回现有会话，不重发需求 |
| 用户真正退出 App（Cmd+Q／退出菜单） | 有未完成工作时提供等待完成后退出、停止后退出、取消退出；完成清理再结束 |

关闭窗口与真正退出的区别已由用户于 2026-09-24 确认。后台状态和重新进入入口必须可见；等待退出时如有待回答交互，应让用户能够重新进入处理或取消退出，不能静默挂起。已有队列属于未完成工作，退出不能悄悄丢弃或重复提交。

**一个 SessionHost 是所有会话连接的公共故障点。**第一版接受这个成本，不为了消除它再上多层监督集群。

OMP 当前 RPC 在 stdin 关闭后会处理待请求、释放会话并退出，因此 Host 崩溃后的恢复，应按“重新启动并读取已保存记录”设计，而不是假设可以重新连接旧 stdio。

所有恢复路径坚持：

> **恢复连接可以自动进行；结果不明的执行命令不能自动重发。**

安全基线固定：Renderer 关闭 Node integration，开启 context isolation 与 sandbox；preload 暴露限定操作；Main 校验通道来源，Host 校验命令和会话归属；模型输出、HTML、链接和附件一律按不可信内容处理。进程隔离不是工具执行沙箱。([Electron][7])

诊断从第一天存在：关联窗口、Host、OMP 实例、会话和请求 ID；默认记录生命周期与错误，不默认记录完整密钥、环境变量和原始对话。提供可预览、脱敏的诊断导出。

# 四、V1 分阶段交付计划

2026-09-24：用户明确本文是完整 V1 的目标架构，按阶段兑现。以下是开发推进计划；不是已完成情况，也不把尚待验证的 ConfigHelper 方案视为定案。

## 推进原则与依赖

主线顺序为：**已有用户单会话可用 → 多会话可用 → 新用户全 GUI 可用 → 体验与规模打磨 → 对外发布。**

每阶段交付可运行的增量，沿用前一阶段的验收样本。基本输入、阅读和工具交互放到阶段 1；数据正确性、安全边界、停止和资源清理随功能实现，不积压到发布前。

认证助手属于提前验证的风险支线：在阶段 1 期间明确首批供应商与认证方式，并做最小验证；该支线不阻塞已有用户的单会话交付，但必须在阶段 3 的完整初始化实现前得出可行结论。这里的支线是工作依赖，不要求多 Agent 或额外团队。

只细化即将实施的阶段。后续阶段保留目标、依赖和验收条件，进入前再形成具体规格，不现在铺开全部工单或建立空目录。

## 阶段 1：已有 OMP 用户能完成一次真实开发

**使用场景：**已安装并配置好兼容 OMP 的用户，在 GUI 中修改测试项目、执行检查并继续同一会话。

交付范围：

- 按已选技术栈搭建单应用，建立 Main、preload、utility SessionHost 和 React 的真实通信链路。协议从开始就带会话身份和实例代次，但只暴露一个活动会话。
- 发现已有 OMP；自动发现失败时允许 GUI 指定可执行文件和有效配置位置。明确显示版本与启动失败原因，不安装或改写用户环境。
- 以真实内置工具验证 `rpc-ui` 的提问／确认／取消；不能用旧 `rpc` 测试扩展结果代替。若有能力缺口，记录具体范围并解决，不静默跳过用户交互。
- 多行输入、中文组合输入、撤销／重做、草稿保留、流式阅读、通用工具卡片展开与复制、正常滚动、追加需求和停止。
- 原生会话正常恢复、Renderer 刷新重连、请求不明时不自动重发；基本进程异常提示和受管理进程清理。
- 正确处理协议分片与超限。先保证输出处理有界且不静默丢失，再根据真实样本优化；未落盘输出不能假定可从历史重新读取。
- 从第一天产生本地 macOS 应用构建，做 Finder 启动与打包资源路径验证。此时不要求对外分发签名，但开发模式成功不能替代本地应用构建验证。

**完成标准：**开发模式与本地构建都能接入真实 OMP；在一次性测试项目完成读文件、修改、命令检查、回答问题、停止、继续和退出恢复。检查实际文件与进程状态，并实际操作输入和阅读界面。模拟模型只能支持自动化，不能代替此验收。

**不包含：**多会话界面、新用户安装／认证、复杂 Diff 和长历史性能优化。它们仍属于完整 V1。

**进入实现前：**修订旧 M1 规格，采用 React 等已确定选型，增加打包接入和 `rpc-ui` 验收；纳入已确定的关窗继续运行、真正退出处理，以及默认排队追加／显式干预行为。其他基础实现选择由实现者决定。

## 提前验证支线：全 GUI 配置助手是否可交付

**启动条件：**明确首批必须支持的供应商、认证方式和是否需要自定义服务地址。此范围需要用户决定，不能由实现者替用户承诺所有认证路径。

只验证影响架构的环节：

- 只有独立 OMP 可执行文件、没有系统 Bun／SDK 时，匹配版本助手如何获得并运行；使用用户级受管理资源，不擅自升级全局环境。
- 至少跑通首批支持集合中涉及的不同认证机制，包括对应的秘密输入／浏览器授权、取消、失败及原生凭据保存。
- 目标配置目录解析一致；配置修改不会整文件覆盖；多进程共享凭据与配置的生效方式有实测依据。
- 助手能从本地应用构建启动，秘密不进入日志或持久化界面缓存。

**交付物：**支持矩阵、可复现原型、实际版本和限制。若 ConfigHelper 不可行，先调整接入方案再实现初始化界面。不要把失败包装成让新用户打开终端的成功路径。

## 阶段 2：多个会话能独立工作

**依赖：**阶段 1 的单会话链路和退出清理已通过；窗口关闭与 App 退出语义沿用阶段 1；会话标签关闭的行为在本阶段细化。

交付范围：

- 会话注册与项目关联，每个活跃顶层会话一个 OMP 进程；切换视图不终止任务。
- 独立请求表、草稿、工具状态及待回答交互，后台摘要和前台详细订阅。
- 历史只读浏览与启动执行分开，接续原生会话，不允许双写同一个原生会话。
- 同目录共享提示、实例资源可见性和安全回收；不抢占执行中、待回答或仍有原生活动的实例。
- Host 镜像、发送队列及大输出都有明确的保留／重读／临时落盘或显式截断策略。丢失增量后重同步不能凭空恢复已丢弃的唯一数据。

**完成标准：**两个真实会话同时运行，包含同项目与不同项目场景；切换后输出、草稿与回答不串会话；停止或杀死一个 OMP 不影响另一个；刷新后各自状态一致；Host 崩溃会准确报告全部受影响会话并清理旧实例，不自动重发。

## 阶段 3：新用户从零进入 GUI，已有用户能管理配置

**依赖：**认证支线通过；阶段 2 提供配置变更作用于多个运行会话的验证环境。

交付范围：

- 环境发现、兼容检查、受管理安装与完整性验证、首批认证方式、模型选择、验证及修复入口。
- OMP、必要的 Bun／助手依赖的来源与版本固定可追踪；取消、网络失败、半成品安装、重试不污染用户既有环境。
- 明确当前会话模型、后续会话默认模型与共享凭据的作用范围；既有 TUI 共用配置时告知变更影响，不静默重启正在执行的会话。
- 支持矩阵以实际验收为准，不支持的路径在 GUI 说明；支持范围内不要求手动终端操作。

**完成标准：**干净测试环境从没有 OMP 开始，完成安装、认证、模型选择、项目打开和真实任务；已有有效环境直接进入且没有非预期配置写入；每条宣称支持的认证路径实际验证成功、取消与失败；运行会话不因设置变化被意外切换或中断。

## 阶段 4：把日常使用体验打磨完整

**依赖：**已有用户和新用户都能进入，多会话已可用。阶段 1 起发现的基础交互缺陷立即修复，不等此阶段。

交付范围：

- 选择与引用、文件入口、常用工具的针对性卡片、详情面板及更完整的输入／阅读体验。
- 从真实输出、长历史与并发任务中建立固定回归样本，测量 Host 内存、消息传输与 Renderer 响应，再选择具体优化。
- 编辑器、Diff、虚拟列表和复杂 Markdown 库按 [前端选型记录](frontend-library-radar.md)与真实样本选择；若改变 OMP 所有权、产品行为或引入商业许可承诺，再与用户对齐。选择“现阶段不需要专门库”也可成立，不为技术清单凑实现。

**完成标准：**用户用 GUI 完成代表性的实际开发任务，输入、查阅输出、引用和回答问题不需要回到 TUI；长输出和并发下能够正常编辑与停止，输出可追溯、资源不无限增长。记录测试样本和观察／测量结果，不用“流畅”二字代替证据。

## 阶段 5：发布候选与 macOS 对外交付

**依赖：**前四阶段完成，认证与 OMP 兼容矩阵已收束；明确对外支持的 macOS 版本和 CPU 架构。

交付范围：

- 汇总故障回归：异常退出、残留进程、会话恢复、共享配置、日志脱敏、安装失败、版本不兼容及开发／打包差异。
- 完成可预览的脱敏诊断导出；阶段 1 起的关联日志用于定位，不能到此时才补日志。
- 使用实际发布资源完成签名、notarization、下载与首次启动验证；缺少开发者账号或签名材料时明确列为外部交付阻碍。
- 在每个对外声明支持的环境验证安装、启动、认证、工作、退出和再次打开。既有环境与干净环境都覆盖。

**完成标准：**真实下载的发布构建完成全流程，无需绕过系统安全提示；任务不擅自重发，原生记录不破坏；交付范围与验证矩阵一致。未验证的平台／架构不列为已支持。

## 当前状态与文档衔接

- 阶段 1 正式 GUI 已存在，规格已修订为 `in-progress`；核心开发路径及未完成验收见 [运行证据](stage1-evidence.md)。
- 当前用户优先级是确认 OMP 多会话、子 Agent、记忆和设置的 GUI 接入可行性；本轮轻量验证及接口缺口见 [Runtime 可行性结论](runtime-feasibility.md)。
- 不以旧阶段验收清单自动扩大本轮范围，也不以本轮 RPC 探针通过宣称完整 V1 或 GUI/TUI 对等已完成。
- 随包 OMP 是后续产品方向；本轮已验证独立二进制启动基础，正式应用打包资源、干净环境与认证尚待验证。

## 最终定案

这套方案保留三个值得长期投入的基础：

**可靠的 SessionHost、清楚的数据所有权、完整的新旧用户进入路径。**

其他复杂度尽量留在真正需要它的地方：OMP 继续处理 Agent，React 继续承载你想打磨的交互；编辑器、Diff、虚拟化等根据真实体验逐个引入。

**第一版不以“拥有多少架构层”为完成标志，而以“你能放心把日常 OMP 工作搬进来”为完成标志。**

# d-pi 无头功能交付

先识别当前授权是调查、文档、验证、实现还是评审；本 skill 不扩大授权，不自行启动原型、安装依赖或提交远端。

## 读取与定位

- 从本 skill 所在目录向上三级得到仓库根，勿把调用时 cwd 当作 skill 目录。
- 读取[决定登记](../../../docs/decisions.md)、[无头功能合同](../../../docs/architecture/headless-features.md)及该功能 spec。阶段范围按[首版方案](../../../.scratch/product-requirements/foundation-plan.md)，行为按[基础契约](../../../docs/architecture/foundation-contracts.md)相关节；已读且未变化的文档不重复加载。
- 标明受影响决定及状态，复用对应版本已有证据。只调查会改变当前实现的未知，不重开整个技术选型。

## 设计或实现

1. 针对当前用户场景，先验证风险最大的接口/失败行为；证据足够就推进。需要 IME/焦点/滚动实验时使用最小界面，不提前建设正式 GUI。
2. 列出本功能的状态拥有者、操作与结果、外部依赖、作用域及释放条件；在当前 spec/任务中记录即可，不自动另建设计文档。
3. 按无头合同区分规则、协调与外部接入、状态投影、React 绑定和视图。核心业务不 import React/DOM，不以 hook 挂载拥有后台任务；Main/Host/OMP 的既有归属不迁移到 Renderer。
4. 组合窄接口，用真实实现与可控测试实现验证同一功能。视图读取与发出意图，不能任意 setState 绕过业务规则；不建立万能 Manager、继承基类或通用状态机框架。
5. **不引入 XState。** 沿用 TypeScript 显式状态转换，Zustand 负责客户端投影，Query 负责异步查询缓存，hooks 做薄接入；不双写权威状态，不自动重发结果未知的提交。
6. 对当前切片分层验收：无 React 的业务/故障测试、真实接口证据、所需订阅与释放检查，随后才是正式 GUI 的交互与视觉验收。诊断随功能交付；无头性能通过不等于 GUI 性能通过。

## 拆票或评审

拆票遵守[本地 issue 约定](../../../docs/agents/issue-tracker.md)。验证/无头/GUI 可以是独立可验收任务，标真正的依赖，不强制每票画界面，不按全应用 store/hooks/pages 横向排工。组件化包含功能组件，不只 UI。正式 GUI 最后接入指每个功能，不是先写全产品逻辑。

评审重点用场景判断：两个消费者是否重复启动任务；卸载视图是否误停后台工作；切换 Thread、迟到结果及重连是否串状态；是否把持久收据或权限藏进 hook；更换呈现方式是否迫使重写业务规则。只报告当前范围有依据的问题。

交付说明所处阶段、合同/拥有者变化、验证证据与仍未覆盖的用户路径。已有授权足够时直接完成，不为每个常规模块或实现细节追加确认。
